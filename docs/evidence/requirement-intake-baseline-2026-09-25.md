# 包装需求整理：首轮真实模型基线

2026-09-25，固定开发集 12 个案例全部开始并得到最终判定，严格任务通过 **0/12**。计划中的 31 个检查点实际到达 24 个，其中 8 个通过、16 个失败；另 7 个因前置阻塞未执行。4 个预留案例没有调用模型。这是当前业务链的失败基线，不是改善收益，也不代表真实客户成功率。

本轮目标是衡量“客户对话与文字附件 → 缺失和冲突识别 → 后续确认与变更 → 带来源、状态和版本的需求单”。输入均为独立编写的合成材料。调用真实 DeepSeek 模型，通过现有 Worker、Runtime、来源工具、队列、Outbox、Fact、Artifact 和 Evaluation 执行；没有用标准答案预填需求字段，没有修改生产代码以配合测试。

## 固定口径和运行条件

输入与预期结果保持 [requirement-intake.v1](../../eval/fixtures/requirement-intake-v1/README.md) 不变。正式运行使用 [v2 执行与评分补充协议](../../eval/fixtures/requirement-intake-v1/scoring-v2.md)。模型配置别名为 `deepseek-v4-flash`，接口为 DeepSeek Anthropic 兼容端点；别名不保证服务方权重长期固定。

每案例最多 32 次生成、160 次计数；阶段执行片最多 8 轮、16 次工具、2 片；输入上限 100,000 Token、输出上限 16,384 Token，案例执行片段上限 10 分钟。生产阶段原有的 120 秒超时和证据复核的 60 秒超时保持不变。费用累计预留上限为 20 美元，实际没有触及费用上限。高费用上限不能消除既有的复核工具预算和超时问题。

“任务通过”要求所有检查点及转换均通过。模型写出 `ready_for_approval` 不足以通过，实际业务状态也必须允许对应版本进入审批。需要澄清的检查点则应阻止审批。模拟员工只确认已观测且有来源的候选；措辞或单位差异经显式评审后才可继续，缺失候选不能由标准答案补齐。

结构、精确数值、状态、来源映射和版本关系采用确定性检查。措辞等价、具体澄清问题、限制条件和禁止声明由案例作者 Codex 辅助评审，逐项绑定检查点哈希；**未盲化、未校准，也不是独立人工专家评分**。工作流内部的模型复核属于被测系统，不是外部评分者。

## 失败定位与最小修复顺序

1. **先修评分器的重复候选处理，再固定新的评分版本。** `eval/requirementIntake.ts` 的 `canonicalCandidate()` 只取同字段的首个候选，RI-10 出现可证实的来源假阴性和错误确认阻塞。用已保存输出增加离线回归，先对旧结果做有版本标识的重新评分；不得静默改写本报告，也不得把评分变化计作产品收益。
2. **修复证据复核的工具契约。** [证据复核调用](../../server/enterprise/evidenceReviewWorkflow.ts) 显式传入 `allowedTools: []`、1 轮和 1 次工具预算，并拒绝出现工具轨迹的结果；[Runtime](../../server/runtime/agentRuntime.ts) 又无条件加入 `context_read` 和 `execution_ledger_read`。本轮 16 个复核响应请求了这些工具，随后以 `budget_exceeded` 结束。需要让“禁止工具”在模型可见工具集合和执行策略中都生效，并用真实 Runtime 合同测试覆盖。不能用提高美元上限替代这一修复。
3. **对齐包装 Skill、Schema 和完成条件。** [Skill](../../src/manufacturing/skills.ts) 只允许七个必填字段，而 [Schema](../../src/manufacturing/requirementBrief.ts) 接受 `material_thickness` 等可选字段。RI-03 的模型明确以字段不被允许为由不登记 0.06 mm。必填、可选但已提供、生产前仍待核实这三种状态应一致表达。澄清输出也应针对缺失项提出具体问题。
4. **保留冲突与来源，不因字段存在就视为解决。** [Worker](../../server/manufacturing/requirementBriefWorker.ts) 按字段命令去重，可能接纳重复候选中的首个值；大部分原始来源引用又被写成 `runtime:<executionId>`。原候选仍持久化，外部评分可回溯，但生产复核获得的证据无法直接解释这种引用。RI-07 的“30 卷不是所需总张数”、RI-10 的内外尺寸属于未解决解释，应阻止采纳单个当前值并明确询问。
5. **补上来源撤回，再验证下游失效。** RI-11 的撤回入口缺失属于产品能力缺口，不能在评测器里删附件来伪装支持。最小闭环应在既有来源、Fact 依赖和 Artifact stale 路径实现撤回，然后验证历史可审计但不再作为有效证据。

上述修复尚未在本轮实施。修复后的对照应保持任务输入、模型配置、输出额度和评分版本一致；开发集固定后再运行未使用的 4 个预留案例。若评分器升级，须先在旧输出上按新协议重评，否则不能直接比较前后分数。

## 协议修订、未知结果与勘误

初始试运行在 RI-01 的证据复核触及 4,096 输出上限后停止，同时发现 `个` 与 `pcs` 的等价单位被判为失败。因此在新的完整运行前公布 v2 协议：输出上限改为 16,384，所有非同字面单位交给显式语义复核。原输入、答案和 manifest 没有变化；初始报告、源码及 USD 0.0167925 预留完整保留。两轮协议不同，不能宣称 v2 比 v1 的产品质量改善。

正式运行的 RI-02、RI-03、RI-13 各有一个复核请求超时。普通续跑会被 `unknown` 账本拒绝。操作员核查后仅在新目录继续其他已经停在评审点的独立案例，携带父报告哈希、完整旧调用、旧预留及逐次排除的案例列表；没有再次执行未知请求所属案例。三个父报告和一次性操作脚本均已归档。这是有审计的评测操作，不是生产 Worker 崩溃自动恢复证据。

RI-13 后续队列记录的 `model_failure / Model token count failed` 源于评测费用保护层发现尚未解决的调用后拒绝继续，并不是又一次向服务商发起计数后失败。该案例在 `evidence_arrived` 后停止，数量变更和最终交接两阶段未验证。

RI-10 的 `clarified` 检查点哈希为 `575cee8b4098a587ec8f2d9a43704cfba6b2428556e0ba7c5760ec1e33fc1cb4`。持久化当前尺寸为 `212 × 162 × 92 mm`，原始模型候选的第二个 dimensions 值相同，来源明确为 `RI-10-S04`。评分器只查看第一个 `200 × 150 × 80 mm` 候选，错误返回无来源；确认守卫复用了该逻辑，导致下一阶段未执行。原始 8/24 检查点分数包含这项假阴性，不能作为无瑕疵的精确测量。即使单独更正这项来源判定，该案例早期的冲突处理仍失败，严格任务通过率仍为 0/12。具体证据见审计文件，不覆盖原始分数。

最终报告仍保留 `status: stopped_unknown`，表示调用账本未结清；12 个任务的评分已经结束、没有待评审项。这两个状态不得混淆。

## 验证与适用范围

离线检查为 4 个测试文件、63 项通过；服务端类型检查通过。测试覆盖固定案例完整性、真实 Worker 的 Fake Provider 联调、禁止注入未观测答案、确认和审批门槛、版本不可变、评审绑定、费用预留与未知结果阻断。离线通过不计入上面的真实模型任务成功率。

模型请求的精确来源 ID 检查未发现其他案例或未来事件 ID 泄漏；这不是完整的语义隔离证明。附件均为文字或元数据，未测试 PDF/OCR，也未贯通 UI/HTTP。每个检查点是由 Outbox 发起的新阶段 Session，跨阶段连续性依靠持久化 Host 状态。本轮没有压缩、Worker 故障注入、进程取消验证、多模型或 Harness 消融对照；实际每案例最多到达 3 个检查点，不能宣称已证明长任务能力。

该结果支持的结论是：项目已经有一组可重复输入、明确完成条件、真实模型轨迹和可定位的失败基线。证明某项 Harness 改进有效，需要在此之后交付保持相同口径的对照结果。
