# 包装需求整理：主要问题修复与复测（2026-09-25）

最终候选在固定 12 个开发案例上严格通过 **9/12**；到达 29/31 个计划检查点，其中 **27/29** 通过。工程修复已落地，但仍有两个叙述质量失败和一次租约失效，不能称为生产就绪。

本轮针对 [固定任务基线](requirement-intake-baseline-2026-09-25.md) 已观察到的失败逐项修复，保持案例输入与 oracle 不变。离线程序行为、真实模型任务表现、评分器更正分开记录。

## 修复方法

| 问题 | 原因与改动 | 防回归证据 |
| --- | --- | --- |
| 只读复核频繁因工具调用耗尽一轮预算 | Enterprise 明确传入空工具列表，但 Runtime 又自动注入读取工具。修正共享适配器：显式 `[]` 真正不提供工具，未指定或非空列表保持原行为。 | Runtime Contract 验证提供给模型的工具为空，越权返回的工具调用被拒绝；不用提高循环次数掩盖问题。 |
| 客户明确给出的 0.06 mm 厚度被忽略 | Skill 手写字段列表与实际 Schema 脱节。改为从 Schema 的必填/可选常量生成指令，要求保留已经提供的可选字段，缺少可选字段不会被算作必填缺失。 | 实际 Worker 测试保留数值、单位和来源；即使模型自称 verified，保存时仍为 unverified。 |
| 冲突尺寸和卷数被当成已解决事实 | Worker 之前逐个写入候选，第一项可能掩盖同字段冲突。先按规范字段聚合；不同值/单位或明确缺失的字段暂不写入本版，冲突值和来源进入待澄清内容。 | 两个尺寸候选不能任选其一；30 卷不能填入未知的总张数。旧记录保留，模型无权拒绝权威事实。 |
| 待确认修改可能覆盖旧值或错误进入交接 | 已确认值保持原样；出现不同候选时由 Host 添加 `pending_fact_change` 并阻止审批。模型只漏写已确认字段时，不能因此撤销已确认内容。 | 即使复核模型返回通过，10000 → 6200 的待确认候选仍被 Host 拦截；单纯省略字段不会产生假冲突。 |
| 原始来源被执行 ID 取代，撤回附件无真实业务入口 | 候选必须引用当前作用域中的原消息、附件或页码。新增员工撤回入口；先持久化撤回记录，再使相关字段、需求单与审批失效。原文件和旧版本保持可审计。 | 覆盖撤回记录已保存但同步尚未执行的中断窗口、重复请求、跨租户、已批准版本、迟到 Worker 与历史工具结果回读。旧 `runtime:` 来源无法定位具体附件时保守要求补充来源并重新核对。 |
| 复核会删掉必要追问 | 必填字段的最低追问由包装规则生成，例如袋尺寸的宽、高、底折、单位和内外口径；叙述修订后再次补齐。字段满足后只移除对应的程序标准问题，保留客户限制。 | 用一次允许的叙述修订复现删问题；验证追问仍在且 Fact 没变。更新 10 项离线 M2 预期，不修改在线案例输入或 oracle。 |
| 变更只写在说明中，后续无法确认 | 模型应输出有来源的 unverified 新候选；Worker 保存旧 verified 值并产生待确认修改，明确人工确认后才能变更。模型候选与正式 Fact 分开处理。 | 10000 → 6200 的 Host 守卫测试；实跑 RI-09 验证提议、确认和版本转换。 |
| 撤回旧尺寸仍被描述成“待核对候选” | 根据持久化 rejected 状态生成“已拒绝或撤回，不可复用，须补新资料”，不再把无效来源描述为可重新确认的候选。 | 已拒绝历史字段的回归；真实撤回案例检查当前字段和完整叙述。 |
| 确定性限制之外仍会丢说明 | Skill/复核明确保留客户明说未定的可选规格、性能、测试条件和硬限制；不为缺少的可选字段建立新必填门槛。 | 用同一固定开发集实跑逐项核对，漏写、误写或额外要求均保留为失败。 |
| RI-10 被评分器错误判为无来源 | 原评分器只取同字段第一个候选。改为匹配字段、值、单位的全部候选，再过滤当前有效来源。确认守卫采用同样的来源边界。 | 固定保存的真实 RI-10 输出作为回归资产；其他值、其他单位和已撤回来源不能借用。 |
| 合法 JSON 被 Markdown 包裹导致中断 | 仅剥除完整的外层代码围栏，再做原严格 JSON/Schema 校验；真正残缺 JSON 仍失败。确定性校验不通过时不再花钱调用语义复核。 | 保存的真实失败输出重放：两项仅有围栏的 JSON 可解析，四项真正残缺仍拒绝。不能把解析重放算作任务成功。 |
| 数值字符串被评分器误判 | `"0.06"` 与 `0.06` 在数值严格等价时转显式复核；没有自动通过，也不做隐式量纲换算。 | 错值、附带单位的数值字符串、失效来源仍被拦截；旧报告另存更正记录。 |

业务规则仍在包装模块；通用 Runtime 只改空工具列表的契约。未新增依赖、多 Agent、模型路由或通用框架。

## 最终实跑测量

- 95 次真实生成：需求整理 65 次、只读证据复核 30 次；另外 190 次 Token 计数请求。这里是模型调用次数，不等同 95 轮用户对话。
- 37 次工具调用，33 次成功、4 次失败（均为需求整理阶段的 `context_read`，三次执行错误、一次输入错误）。失败后相关案例完成；这仍是待改进项，不能宣称整体工具成功率提升。
- 复核阶段 30 次调用没有请求工具；原基线 24 次复核调用中有 16 次请求工具并触及预算错误。本轮没有已捕获的复核预算失败，但其中一次调用因租约失效成为 unknown。
- 记录的案例执行耗时中位数 84.0 秒，范围 24.5–212.3 秒；总计 1140.0 秒。排除案例间人工评分等待，但包含执行期间的请求等待和调度影响。到达工作量不同，且超时配置改变，不计算“效率提升百分比”。
- Token：非缓存输入 116952、缓存输入 193920、输出 154088。没有 Compact 事件，不能报告压缩节约或信息保留率。
- Trial C 已知 usage 费用估算约 USD 0.2212；连同基线及前几轮累计已知约 USD 0.8967。累计保守预留 USD 6.4163，授权上限 USD 20。保留 8 个历史/本轮未知调用，费用未对账，不把估算当账单。
- RI-13 连续跟单贯穿 9 份来源、16 个投递/确认/评测事件、5 个检查点和 5 版需求单，使用 15 次模型生成、5 次工具读取，约 168.4 秒；最终保留禁 PVC、原交期、稿件状态、样本检测条件和新数量确认。它是多阶段连续性证据，不是超长上下文或百轮工具压力测试。

## 故障窗口与证据边界

- 附件撤回先落不可变记录，随后更新事实和审批。若两步间崩溃，下一次读取/启动/交付检查补做同步；不会重新调模型。重复撤回输入相同则幂等；同一请求 ID 改换原因，或提交不同文件哈希则冲突。
- 正在执行的任务要求先停止再撤回。即使出现并发迟到响应，Worker 写入前仍比较附件摘要；缓存工具结果也按当前来源摘要验证。历史版本和原文件仅供审计，不作为当前事实证据。
- 已确认数量收到新提议时，模型不得覆盖旧值；Host 的待确认守卫独立于复核模型的“通过”。人工确认记录绑定具体字段版本与原始提议。
- 已发送模型请求的结果不确定时保留 `unknown` 和预算预留。只对其他全部调用已知、状态已持久化的独立案例做人工审核续跑，保留父报告哈希和排除列表。这个一次性操作不是自动崩溃恢复成功率。
- Token/cost 来自真实响应 usage；未知响应不编造费用。保守预留按发送前计数和输出上限计算，不退还，不能等同最终账单。没有发生 Compact 时不计算 Token 节约率。

Trial C 出现一次真实 `lease_lost`：RI-14 的复核请求无已知响应，记录等待约 197 秒，超过 120 秒配置期限，恢复检查时租约已失效。该现象说明墙钟时间、进程调度和定时器超时不能混为一谈；本轮没有证据单独归因于服务商、宿主休眠或事件循环停顿。旧 Worker 停止写入，保留未知请求与预留，RI-14 按任务失败计算。没有延长过期租约、重放请求或把安全停止计成任务成功。
