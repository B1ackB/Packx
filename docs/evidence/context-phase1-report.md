# 上下文第一阶段：任务整理、压缩与回读

日期：2026-09-22。基线提交 `da4fcd1`；本报告记录基于该提交完成的第一阶段实现与验证。用户授权独立测试及所接 DeepSeek 的有限实验。

## 当前结论

第一阶段已实现“原话完整保存 → 人工整理候选 → 明确确认 → 有界任务状态 → 压缩工作消息 → 带来源验证的回读”。没有加入自动记忆 Agent 或让摘要模型修改业务事实。

默认建议暂保留 **70,000 Token 触发、45,000 Token 目标、100,000 Token 应用输入上限**。这是保守起点，不是已经证明的最优值。32k/20k 在本合成任务中更省输入，但样本没有覆盖广泛长任务信息损失；100k/70k 增加输入量，没有显示质量收益。

后续核验见[第二轮验证报告](context-continuation-verification.md)：补测多轮压缩、真实回读查询及依赖边界，发现新增失败场景。本报告的 6/6 仅对应下述第一阶段协议，不能作为所有后续实验的通过率。

## 本次落实的内容

- 新增当前任务专属的阶段整理记录，包括目标、有效要求、待解决事项、进展笔记。候选不会替代历史；只有用户确认后生效，旧版本保留，新的用户消息继续原样进入任务上下文。
- 12 次整理、480 条合成原始用户消息的固定测试中，每次确认后的任务上下文均小于 4,000 字符，原话全部保留。另由独立测试员从真实 `ConversationApi.send` 入口验证：80 条历史超过 64k 时先明确拒绝；确认整理后可继续，任务上下文小于 5k。
- 业务 Fact、当前待确认值、旧已确认值、Artifact 和审批仍由 Host 提供。进展笔记不证明 Stage 完成。完整 raw transcript 不因整理而删除；模型跨依赖回读 transcript 时仅暴露原始用户消息，正式助手历史仍在 UI 中。
- 整理使用 SQLite 事务事件、版本 CAS、命令去重与来源哈希。附件变化、新消息、过期版本、跨任务/租户/工作区和慢请求竞态均有回归。
- 修复回读内容再次压缩后的来源链，兼容旧完整工具批次及旧单条外置封套；恢复、计数和发送模型前重新检查来源。来源撤回时停止，避免把已撤回内容再次发给模型。
- 明确 JSON 数组分页参数：`sourceRef`、`messageIndex`、`jsonPointer`、`offset`；遗漏 messageIndex 时不再静默忽略 JSON 选择参数。
- 上下文过大或来源暂不可用时仍可查看、暂停、取消、退出 Plan；开始/确认/恢复执行仍受原来源和版本检查。

使用入口：右侧工作区 **记忆 → 整理当前任务的要求与进展**。第一阶段由用户填写并核对，不会自行推断哪些要求已失效；未整理原话累计 16k 字符时显示提示。重新启动 Host 后加载此次服务端实现，本次没有重启真实使用中的 Host。

## 实际 DeepSeek 与大小单位

读取的配置为 `BLACKX_RUNTIME_MODE=anthropic`、官方 `https://api.deepseek.com/anthropic`、模型名 `deepseek-v4-flash`。未读取到用户覆盖的上下文阈值，没有改动真实密钥或模型选择。

核对的[官方模型及价格文档](https://api-docs.deepseek.com/quick_start/pricing/)说明旧 `deepseek-v4-flash` 名称仍可用，但请求由 DeepSeek-V4.1-Flash 服务；上下文容量为 1M Token。[Anthropic 兼容文档](https://api-docs.deepseek.com/guides/anthropic_api/)确认当前端点及 Tool 协议。实验响应的 `model` 字段仍回报旧名称，所以底层版本映射是官方说明，不能由响应别名单独推断。

| 数值 | 含义 | 本次处理 |
| --- | --- | --- |
| 1,000,000 Token | 已核对的官方 Flash 模型窗口容量 | Host 识别官方端点及已知模型；未知端点不套用 |
| 100,000 Token | Packx 的应用输入硬上限 | 保留，不把 1M 当日常输入目标 |
| 70,000 / 45,000 Token | 压缩触发 / 目标 | 保留平衡起点，增加显式配置和启动校验 |
| 24,000 字符 | 无 Provider token counter 时 ContextEngine 的后备触发值 | 不作为真实 DeepSeek 的正常触发值 |
| 16,000 字符 | 未整理用户原话的 UI 提示 | 提醒整理，不自动删减 |
| 64,000 / 32,000 字符 | 必留任务上下文 / Plan 输入上限 | 保留明确失败边界；先整理可减少历史要求部分 |

中文、英文、JSON、工具定义和图片无法用一个固定字符比例换算。正常路径使用 Provider token counter；目标值允许加入摘要、必要消息后略有超过，但不得越过输入硬上限。

## 真实阈值对照

最终协议见 [run5 原始报告](context-thresholds-online-run5.json)。两份合成 fixture 使用相同结构但不同订单数量/证据码；每份约 43 万字符，包含 110 组历史工具结果，且三个配置共享同一 fixtureHash。每例经真实 Runtime 压缩与模型 Tool Calling，回读第 87 行原始表格；按确定性 oracle 检查确认总量、待确认新总量、PVC 禁用、100 µm、供应商未核验、证据码、引用位置和测试条件八项。

| 触发 / 目标 Token | 最终协议通过样本 | 主请求最终输入 Token，两个样本 | 每例成功回读 | 每例生成调用 | 总耗时，两个样本 |
| --- | --- | --- | --- | --- | --- |
| 32,000 / 20,000 | 2/2，各 8/8 字段 | 23,055 / 23,126 | 1 | 4 次摘要 + 2 次主调用 | 18.8 / 14.3 秒 |
| 70,000 / 45,000 | 2/2，各 8/8 字段 | 47,308 / 47,199 | 1 | 4 次摘要 + 2 次主调用 | 14.3 / 13.9 秒 |
| 100,000 / 70,000 | 2/2，各 8/8 字段 | 72,767 / 72,429 | 1 | 4 次摘要 + 2 次主调用 | 16.4 / 14.5 秒 |

同一 seed 的三个配置使用同模型、同输入、同输出上限、同迭代/工具预算。对照统一使用 180k 应用输入上限以容纳候选配置，最终主请求均低于生产默认 100k；不能据此声称跑过所有生产预算组合。脚本缓存相同请求的 token-count 结果，供应商也存在前缀缓存，且运行顺序固定，所以耗时不能用来判定哪档普遍更快。

**摘要并未完整覆盖被移除历史。** 三档均只在四次摘要预算内覆盖 17 条消息，而被移除消息分别为 186、144、100 条；其余明确标为 INCOMPLETE 并保留归档。通过样本证明了当前 Host 状态和明确指定来源的回读，不能证明所有旧细节被模型记住。本轮也没有评价多次真实压缩后的长期漂移、未知来源的发现能力、图片/生产文档质量或自然语言冲突自动解决。

## 原始失败与费用

所有运行保留，不删除失败或只报告最好结果：

1. [run1](context-thresholds-online.json)：当前执行沙箱拒绝网络计数请求，0 次生成调用。
2. [run2](context-thresholds-online-run2.json)：一例通过，下一例达到四次工具执行上限；13 次生成均有完成回执。
3. [run3](context-thresholds-online-run3.json)：回读参数不明确，模型反复调整分页并达到八次工具上限；10 次生成均有完成回执。随后明确接口参数和错误信息。
4. [run4](context-thresholds-online-run4.json)：六例回读均成功，但四例把 pendingQuantity 解释成新旧总量之差 1,000。该字段原 Schema 没有解释总量/增量语义，因此不能把这些失败归因为压缩丢失。
5. [run5](context-thresholds-online-run5.json)：对全部配置统一增加“待确认的新总量，不是增量”的字段定义，六例均通过。这个协议变更与修复后的结果不能伪装成同协议提升，也没有据此修改业务 Fact 或放松 oracle。

累计 95 次生成调用，均有完成回执；脚本逐次持久化 started/completed/未知状态，不自动重放结果未知的付费请求。运行预算预留累计 **0.685262 美元**，低于总上限 1 美元。返回用量累计为非缓存输入 678,442、缓存输入 909,440、输出 27,513 Token。

按核对时的官方 Flash 峰价（每百万非缓存输入 0.3 美元、缓存输入 0.006 美元、输出 1.2 美元）估算为 **0.242005 美元**；完全忽略缓存优惠则为 **0.509380 美元**。这是返回用量的价格估算，不是账户账单核销。原始报告记录价格依据和保守预留，未包含真实用户会话或密钥。
