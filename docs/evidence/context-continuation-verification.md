# 压缩与回读：第二轮核验

日期：2026-09-22。被测实现为已合并的 `main 555d79c`（PR #17）。本轮增加验证资产，没有修改生产策略、默认阈值或用户会话。

## 结论与修正

第一阶段的保存、来源校验和确认边界有回归证据，但真实模型在多轮压缩后发现资料、读完后完成任务的能力仍不稳定。70k/45k 只能作为当前保守默认值，不能称为经过充分验证的最优配置。

- 3／5／10 次压缩并逐轮重建文件 Store 后，固定原文、完整工具组和来源撤回校验均通过；这些是确定性机制测试，不代表真实模型能自主找到资料。
- 超大无换行单条内容保存完整，但当前通用回读仍无法读出。后续摘要的 `Coverage: complete` 只表示处理了直接输入，不能证明早期遗漏被补齐。
- 新的真实 DeepSeek 实验在当前 70k/45k 阈值、100k 应用输入上限下完成三轮压缩；两个后续查询均触发实验工具预算，未形成最终答案。其中一个已经读到所需原文，仍继续查找。
- 现有模型监控已展示 Token、缓存、延迟、成功/失败和逐次请求；后端也记录 summary purpose。上一轮“让上下文状态透明”的建议应收窄为输入构成、主调用/摘要分项、覆盖状态及回读表现的展示，不是从零建设监控。

## 新增独立机制验证

测试文件：[compressionContinuation.audit.test.ts](../../server/runtime/compressionContinuation.audit.test.ts)。Fake 摘要刻意省略原文内容；消费者主动沿精确引用访问归档，因此测试通过只证明可达性和边界。

| 场景 | 证据与结果 |
| --- | --- |
| 3／5／10 轮实际 Runtime → ContextEngine 压缩，每轮重新创建 FileAgentStateStore | 原文逐字相等；双工具调用和结果组保持完整；来源撤回后生成和 Token Count 均为 0 |
| 160 行大工具结果真实外置，再压缩 10 轮并重建 Store | 从当前摘要沿归档和正文引用分页，全部行逐条相等，单位、条件、未确认状态均保留 |
| 约 32k 字符无换行单条消息 | 原文完整存于归档及 transcript；默认回读和 messageIndex 选择均返回空 items、single_unit_exceeds_budget、nextOffset: 0 |
| 上述超大消息继续被摘要两轮 | Fake 没有复述旧标记时，Host 可显示 Coverage: complete，原文却仍不可分页读取；早期遗漏没有结构化继承 |
| 实际持续压缩触达依赖边界 | 此构造下第 128 次成功，第 129 次新增依赖后返回不可重试 context_failure；该轮摘要生成 1 次、主生成 0 次，原工作历史不变 |

128 是单次校验允许访问的唯一来源引用数，不能解释成所有任务都能压缩 128 轮。不同工具、归档和分支会改变到达上限的时机。本轮未改变上限，也未把上述失败路径修复为可继续执行。

## 新的真实模型实验

执行脚本：[contextContinuationVerify.ts](../../eval/contextContinuationVerify.ts)。原始回执：[context-continuation-online.json](context-continuation-online.json)。请求快照的离线复核：[context-continuation-replay.json](context-continuation-replay.json)，包含原始回执 SHA-256。

协议在调用前固定：单份合成 fixture，223 条历史消息、序列化约 44.5 万字符；数量与待确认数量由 Host 提供，材料禁令/单位/供应商状态只在历史中，检测代码/温湿度/引用只在中部工具结果中。每轮追加无关历史并重建文件 Store，使用真实默认压缩阈值。第三轮后从同一检查点复制两份状态，分别询问不带源位置和带精确位置的问题，两个答案不会互相污染。

实验限制为每轮 9 次主迭代、8 次工具执行、180 秒，与第一阶段阈值对照的工具预算一致。**普通 Runtime 默认允许 32 次迭代、64 次工具执行，普通会话超时为 120 秒；本轮没有复测该完整生产预算组合。** 因而下面的预算失败不能直接推断为生产默认预算必然失败。

| 阶段 | 结果 |
| --- | --- |
| 未压缩理解对照 | 最终答案 10/10 字段正确；另有一次猜测来源名的回读失败，正确答案可直接从仍在上下文中的原文得到。这不是一次成功回读的证明 |
| 压缩第 1 轮 | 移除 146 条，摘要覆盖 17 条；主请求 45,396 Token |
| 压缩第 2 轮 | 移除 142 条，摘要覆盖 17 条；主请求 46,539 Token |
| 压缩第 3 轮 | 移除 142 条，摘要覆盖 16 条；主请求 46,665 Token。原始检测结果及其证据码均已不在工作上下文 |
| 三轮后，不提供来源位置 | 执行两次工具后，又批量请求 10 个回读；整批超出预算而拒绝，未读到检测原文、没有最终答案。最后输入 49,834 Token |
| 同一检查点，提供精确位置 | 第一次回读已将正确检测原文送入下一次模型请求；此后继续读其他位置和执行账本。累计执行 7 次工具后又请求 4 次，整批拒绝，没有最终答案。最后输入 53,267 Token |

两条查询均是 `budget_exceeded`，不是达到了输入 Token 上限。不能写成“实际执行了 8 次工具”，因为 Host 在执行整批调用前检查剩余预算。这些反例证明当前受控条件下的资料发现和完成行为存在不足；一次 fixture、一次采样不能给出普遍失败率，也不能区分改检索、改完成提示或增加工具额度分别能改善多少。

本轮共 25 次生成（12 次摘要、13 次主调用），31 次 Token Count 网络请求；所有生成均有 completed 回执，未重放失败查询，也没有修改问题后挑选通过结果。脚本因为包含两条失败查询而退出 1，这是记录到负面评测结果，不是把负面结果删除或当成质量通过。

调用后仅加固了 CLI 的台账入口：追加实验必须显式传入经核对的累计 `--prior-report`，不能只换输出路径沿用 run5 的旧预留数。没有因此重新调用模型；原始回执保留执行时脚本哈希和原协议。`--plan` 可离线查看固定 fixture 与实验步骤，真实调用还需显式 `--online`，已有报告拒绝覆盖。

新增非缓存输入 224,997、缓存输入 350,336、输出 7,753 Token，按官方峰价估算 **0.078905 美元**；连同第一阶段约 **0.320910 美元**。保守预算预留累计 **0.929132 / 1 美元**。价格估算不是账户账单。原始记录只有合成数据，无真实会话或密钥。

“新增测试通过”表示成功固定已知机制和限制，其中包含故意断言回读失败、覆盖标记变化与依赖超限；不表示这些限制已经修好。

后续应优先验证以下改进，每项都用本轮失败 fixture 对照：

1. 完整回读与资料定位：超大单元分片、归档消息索引/关键词定位，保留逐次权限和来源校验。
2. 有界完成行为：让模型知道剩余工具预算，并在已有证据足够或仍有缺项时形成明确结果；不能靠放宽质量标准得到成功。
3. 跨轮覆盖状态和来源依赖整理：结构化保留尚未概括/尚未核实的范围，在达到依赖上限前提供可确认的整理/重建路径。
4. 自动提议任务整理与可视化分项：沿现有候选→确认和监控机制增量实现。
