## 1. 要证明的价值

目标任务：输入逐步到达的客户对话与资料，输出可核对、可追溯、版本正确的需求单；缺资料时暴露缺口，有变更时保留当前事实和待确认提议，故障后给出可验证的继续或停止状态。

首先验证三项工程价值：减少错误事实及失效审批；在固定预算内完成规定的结构化工作；发生故障时不重复已发生的副作用。没有真实参与者时，不估计员工节省时间、满意度、付费意愿或生产订单收益。固定合成任务支持限定范围内的能力结论，不代表真实客户分布。

落点遵守现有分层：包装答案和业务评分在 Domain Eval；状态、审批、恢复证据来自 Enterprise；模型、工具、上下文记录沿用 Runtime/Core。优先扩展现有评测，不新增通用评测平台、Judge 框架、多 Agent 或路由。

## 3. 无人工条件下的评分设计

### 3.1 三类结果分列

1. **程序可判结果**：字段值、规范单位、确认状态、明确来源 ID 关联、缺失集合、待确认变更、版本和审批状态、是否实际保存 Artifact、是否重复写入。
2. **未决语义结果**：自由叙述是否完整、澄清是否自然且充分、引文是否语义上支持推断、额外建议是否合适。保持待复核，不能靠关键词命中自动通过。
3. **可选模型辅助判定**：独立调用、固定规则、隐藏候选版本身份，要求判定、原文证据、理由和 unknown。生产工作流的 Reviewer 是被测组件，不能同时作为最终评分者。无人工校准时，Judge 结果只作辅助；多模型一致也不等于专家正确。

来源 ID 对得上只证明引用关联，不能证明原文蕴含结论。输入中存在某个数字也不能证明该数字用于正确产品、字段或单位。

### 3.2 自动任务协议与原完整任务协议分开

保留 [v1 素材和历次评分](requirement-intake-evaluation.md)。已新增[版本化自动任务协议](../eval/fixtures/requirement-automatic-v1/README.md)，终点定义为“规定的结构化需求状态已形成，等待应有的人工核对”，不把全部自由叙述正确或生产交付纳入自动通过的声明。

现有执行器在字段语义等价未决、模拟审批条件未满足时会暂停。不能简单删除这些条件跑满案例。处理方式：

- 对允许的字段格式、别名、单位表示，先定义有限规范化规则及反例，再冻结；未覆盖表示返回 unknown，不临时将错误迁就为正确。
- 模拟确认仅对 Agent 已正确提取、来源和状态匹配的候选执行。不能预填本轮待提取答案，也不能用测试脚本补齐遗漏。
- 自动任务不在待语义核对时批准新交付物。需要验证旧审批失效的场景，可从明确标注的“已有已批准订单”初始状态开始；该状态为双方相同的前置条件，新变更仍由 Agent 从新资料提取。
- 新批准流程和全部叙述质量继续保留在原完整任务协议；状态机审批契约可另用 Fake 离线验证，不能混进真实模型自动任务成功率。
- 提取和任务完成均检查实际 Fact/Artifact/事件状态，不用模型的“完成”声明作证据。

### 3.3 首批 12 个场景的范围

以下是协议的场景设计，已形成 12 场景／31 检查点的冻结任务集并用 Fake 参考输出验证，尚未运行真实模型。素材复用已使用的 development 资料，不读取预留答案来调策略。每个场景含正向完成条件和禁止行为。

| 场景 | 自动判定终点 | 必须防止的错误 |
| --- | --- | --- |
| A01 明确完整需求 | 七个必填字段及原来源正确，待人工核对 | 擅自 verified 或自动批准 |
| A02 对话与文字附件拼接 | 按两个已到达来源补齐同一订单 | 从其他订单／未到达资料补答案 |
| A03 数字与单位表示 | 冻结的等价表示正确规范化 | 将卷数当总张数、单位不一致却通过 |
| A04 缺少必要信息 | 正确字段集合与缺口状态 | 猜测缺失尺寸；全部拒绝也不能通过其他完整场景 |
| A05 同字段冲突 | 保留冲突或缺口，不能任择一个确定值 | 第一候选覆盖冲突 |
| A06 可选规格未提供 | 不新增虚构 Fact 或必填缺口 | 结构正确不代表自由说明中的额外待办已经正确 |
| A07 已确认值收到提议 | 旧值保留，pending change 可追溯，审批受阻 | 新提议直接覆盖 confirmed 值 |
| A08 明确确认变更 | 严格匹配候选后推进版本，旧交付失效 | 借确认脚本把 Agent 漏掉的答案写入 |
| A09 来源撤回 | 当前证据不可用、对应字段重新要求核对 | 通过缓存／旧摘要重新引用撤回正文 |
| A10 附件包含指令注入 | Fact、工具权限、审批无未授权变化 | 单凭叙述没出现关键字就宣布抵抗注入成功 |
| A11 来源版本错配／无正文 | 保持缺口和阻断，不编造解析结果 | 把文字元数据测试称作真实 OCR 评测 |
| A12 连续跟单 | 多个规定检查点均正确，来源／变更／版本连续 | 最终正确掩盖中间错误；多次阶段 Session 冒充单一长会话 |

答案先于运行确定，oracle、未来事件和评分规则不进入模型请求。初始规范数据与新待提取信息明确分开。自然语言来源先使用有明确映射的独立编写文本；模型改写只能增加候选素材，不能自动生成可信金标准。不同措辞变体属于同一任务家族，不能用换数字凑独立样本数。

### 3.4 评分器也必须验收

每类至少有一份已知可接受输出及一份故意破坏的输出。破坏数量、单位、来源、确认状态、旧审批、版本或删去关键字段时必须被拒绝；合法格式差异不能一概判错。保留预期判定及评分器版本，报告漏检和误判。

计划初稿新增的 5 项审计测试只验证“历史报告的统计与证据绑定”，不等价于完成上述新任务评分器的全部资格验证。原执行器已有防答案注入、错误候选不确认、复核绑定与审批门禁测试，继续复用。后续已新增自动评分器资格验证：31 个参考检查点通过，数量、单位、来源、状态、审批、Artifact 和 pending change 破坏反例不能通过；这不是模型任务成功率。

## 4. 对照实验与统计口径

### 4.1 首轮：同模型的两个版本

先冻结任务、评分、模型端点及别名、输入／输出预算、工具／迭代上限、阶段／复核超时、上下文配置、价格口径、代码和依赖哈希、请求顺序、停止规则，再启动模型调用。使用独立数据目录和作用域，隔离记忆与运行状态。

首选上一份可重现的候选代码与当前候选，采用同一新协议。如果比较整个修复组合，就明确标为组合改动；证明某一机制的作用时，另做只改这一机制的对照，不删除两边的事实、权限、审批保护。新旧 `pendingChanges` 的 Schema 行为不同，旧 v1 oracle 不能直接无版本改成新答案后计算提升。

先用独立开发冒烟样例验证完整采集与评分，然后冻结正式实验。预设 12 个场景 × 2 个配置 × 3 次独立尝试 = **72 次任务运行**，不是 72 次模型请求。轮换／交错版本执行顺序并记录缓存和时间，失败不能只重跑到通过。三次重复仅能观察初步稳定性，不能支撑生产 p95 或高置信泛化结论。

更换模型是下一项独立实验：固定同一 Harness 与协议，对第二个已接入、预算已核实的模型重跑相同场景和重复次数；语义、工具使用、成本和失败类别分别报告。跨模型不改题、不调各自 Prompt 后混称同一条件。Provider Contract 通过只说明接口行为，不能证明替换模型不退化。

费用必须按冻结模型的实际费率和每任务限制核算全批预留；历史 20 美元批次和其中未知调用不能自动充当新实验授权或清零。本轮已冻结模型配置、两个可重现生产代码快照、新任务 manifest 及 72 + 36 次任务顺序；本轮总费用上限尚未确定，在线实验尚未启动。不得将旧批次授权挪用为新额度。

### 4.2 主指标与分母

| 指标 | 口径 |
| --- | --- |
| 自动协议任务通过率 | 该任务全部必需检查点与转换通过的尝试／全部已开始尝试；始终注明是结构化自动协议 |
| 覆盖 | 计划、开始、到达、通过、待判、失败、未知、未开始各自计数；未开始也须披露，避免只启动容易案例 |
| 稳定性 | 每个案例三次结果，以及三次均通过案例数／12；重复次数不是不同任务数 |
| 关键错误 | 错事实确认、越权、失效来源、旧审批误用等逐项计数，任一发生则本次任务失败 |
| 误阻断 | 预先标为可完成的场景中被错误阻断的比例；不能靠一律拒绝获得安全高分 |
| 工具 | 实际执行次数、成功／failed／denied／unknown、输入错误／执行错误、重复读取；申请但未执行单列 |
| 时间 | 全部尝试及通过尝试分别列耗时，中位数和范围；阶段等待、模型、工具、重试、审批等待分开 |
| Token 与成本 | 包含整理、复核、摘要、重试、失败尝试和必要计数请求；缓存、输出、未知用量分列；单价估算与账单分开 |
| 每个成功任务的代价 | 同一实验臂全部尝试已知成本／成功次数；无成功则不可计算，有未知用量则仅为已知部分，不给虚假精确总价 |
| 失败归因 | 保留失败节点、错误码、是否实际重试／降级、需何种处置、副作用是否未知；根因无法确定就保留未知 |

不把单个字段、检查点、模型调用当独立任务。业务层阻断可以是正确结果，但只有符合该场景预期终点才算通过。状态恢复成功、安全停止和业务任务完成必须分别计数。

自动协议通过只能证明规定结果。若另做普通聊天／单次 JSON 输出对照，应采用相同来源、共享可评分结果和预算，明确这是产品方案比较；不能因聊天没有数据库而把所有版本／恢复分都记成 Harness 的推理收益。

### 4.3 改进循环

固定基线 → 保存全部轨迹与失败 → 定位最主要的一个失败机制 → 最小修复并增加回归 → 同协议复跑 → 检查收益与代价 → 才决定保留。关键违规不能被平均分掩盖；提高成功率时也列出新增成本和误阻断。未观察到收益则保留负结果，不扩大实现复杂度。

## 5. 长任务与上下文专项

“长任务”至少分三种：多阶段业务连续性、大上下文内的读取／压缩，以及中断后的持久化恢复。每次报告实际阶段、来源、消息、输入 Token、生成／工具次数、墙钟时长和中断位置。

现有 RI-13 历史证据是 9 份来源、16 个事件、5 个检查点／需求单版本、15 次生成、5 次工具读取、约 168.4 秒。它支持多阶段连续性，尚不支持数小时、百轮工具或超长上下文声明。

已有 [12 组长上下文回读实验](evidence/context-long-readback-completion.md)：三个历史状态 × 两工具版本 × 两次重复，固定十字段均通过；主调用合计旧版 21、新版 14，工具总数两边均为 36，且新版已知费用估算更高。历史状态来自三轮压缩，但这 12 组查询没有新增压缩。它支持特定回读改进的正负结果，不是整个持续任务的压缩净收益评估。

已实现并冻结的[连续压缩执行器](../eval/contextContinuous.ts)复用已有上下文能力，在线尚未执行。当前执行器覆盖单一 Session 六批资料、两种阈值、确认／待确认事实与已知索引原文回读；真实压缩次数、摘要覆盖与总费用必须由在线结果给出。原计划的更广泛验收目标如下；任意搜索、未决待办语义和来源撤回后的真实模型行为仍需后续场景，不能从当前执行器推断：

- 压缩后的当前状态保真；需要时是否能读回原文；来源撤回后是否仍会错误恢复。
- 完成任务的总 Token／成本，包括摘要和补读开销；单次请求缩小不等于总成本降低。
- 回读次数、无效搜索、读取充分后是否继续搜索、任务是否在预算内完成。
- 各阶段真实输入量及是否触发压缩。超出模型可承载范围的“不压缩”基线只能记预算失败，不据此捏造等量 Token 节省百分比。

## 6. 故障窗口、取消与事件边界

| 故障窗口 | 当前实现／证据 | 下一步可验证完成条件 |
| --- | --- | --- |
| 租约到期，旧 Worker 仍返回 | 队列按 leaseId、owner、过期时间校验；Scheduler 在心跳及提交边界 renew／assert；已有旧 Worker 迟到 Artifact 被拒的离线测试 | 真实双进程抢占和迟到提交，确认旧 Worker 不能提交业务状态；不把本地检查当远程服务的 fencing token |
| 副作用完成，回执未存 | 本地文件有审批意图、备份与后置条件对账；已有真实 SIGKILL 实验 | 证据匹配则补齐记录且不重写；外部改动则保持未决；覆盖范围逐工具列出 |
| 回执已存，执行账本未完成 | 本地文件可从不可变回执修复账本，已有 SIGKILL 实验 | 恢复后一次结果、零重复写；另记录检测／对账时长 |
| 模型返回，Session／Checkpoint 未存 | 生产遥测保存 running／结果元数据，Loop 与 Session 在后续边界保存；无统一原子事务 | 单独注入崩溃，查明是否再生成、是否重复计费、是否重复工具；不能沿用评测脚本的未知请求保证 |
| 正式回复已存，completed Trace 未存 | Runtime 原轮回放要求 completed Trace，缺失则停止；已有恢复单测 | 真实进程故障验证停止且不重发；自动补写目前不是既有保证 |
| Event／Outbox 提交后、Queue 入队或 ACK 前 | 当前文件 EventStore 同次写入业务事件和 Outbox；确定性 Job 身份处理重投 | 分别验证重复投递不创建重复业务任务，持久失败和残留锁可被诊断；Outbox 当前没有全局总尝试次数上限 |
| 用户取消，模型仍在远端执行 | AbortSignal 停止 Host 等待和后续提交；无法保证服务商已经终止计算或退费 | 分别记录取消响应、迟到结果、后续提交／费用状态，不写“取消即撤销” |
| 用户取消／Host 崩溃，原生解析子进程仍在 | 沙箱进程组 SIGTERM／SIGKILL 与 supervisor 已有原生测试 | 验证子进程确实退出且无迟到提交；与网络请求取消分开报告 |

代码依据：[队列](../src/enterprise/stageJobQueue.ts)、[Scheduler](../server/workers/stageJobScheduler.ts)、[旧 Worker 测试](../server/workers/stageJobScheduler.test.ts)、[Runtime](../server/runtime/agentRuntime.ts)、[模型遥测](../server/runtime/modelTelemetry.ts)、[原生执行器](../server/runtime/macOsSeatbeltSandboxedToolExecutor.ts)、[恢复说明](reliability-recovery.md)。

特别区分：`eval/requirementIntakeRun.ts` 的 boundedProvider 是实验费用与请求账本，不等同生产 Runtime 的通用模型请求事务。遥测、Session、Trace、工具账本、业务 Event 是不同存储；一次模型调用成功不等于业务提交成功。只读生成的重复费用与写工具的重复副作用也不是同一个保证。

### Event Sourcing 的真实范围

[ProposalRunEngine](../src/enterprise/proposalRunEngine.ts) 通过事件 reducer 重建其业务聚合，包括事实版本、交付物元数据、审批和阶段状态。不能说仅有 Event 日志就能恢复整个应用：Artifact 正文、附件／原文件、Session／ContextSnapshot、工具回执／账本、Queue、模型遥测等仍由各自存储保存。

[FileEventStore](../server/enterprise/fileEventStore.ts) 当前文件格式为 v3，存在 v2 事件文件加载为 v3 且 Outbox 为空的兼容路径；这不等于所有历史业务事件都有完整版本迁移。事件字段变更需旧日志夹具、重放等价和显式兼容规则。重放 reducer 只重建状态，不重发模型请求、发送消息、执行工具或再次发布。

后续验收：旧格式日志重放后的业务状态一致；未知／损坏事件安全失败；缺失 Artifact blob 能被报告而非伪造恢复成功；整个恢复过程没有外部副作用。不要为写上 Event Sourcing 而先造通用迁移框架。

## 7. 原问题逐项覆盖审计

“已有”均限于链接中的范围，不表示本轮重新执行过所有历史实验。

| 最初提出的问题 | 当前证据 | 还缺什么／优先级 |
| --- | --- | --- |
| Harness 是否使任务完成得更好 | 固定需求开发集基线、修复和真实模型轨迹已有；9/12 有复核依赖和条件变化 | P1：同协议同预算重复对照；新增自动协议不能与旧完整评分直接相减 |
| 长任务到底多长、多少工具轮次 | RI-13 多阶段数据及独立长上下文回读数据已有 | P1：连续大上下文任务的实际规模与中断；模型调用、工具调用、阶段分别计数 |
| 什么叫成功 | 现有业务结果、检查点、版本与权限判定明确 | P0：无人时单独定义自动终点；不丢未决语义与未到达阶段 |
| 换模型会不会退化 | 有 Provider 契约，当前任务报告主要是同一模型 | P1：固定 Harness 的第二模型真实任务对照 |
| 压缩省多少 Token、丢多少信息 | 有专门压缩／回读实验，但需求任务 Trial C 没有 Compact | P1：实际连续压缩后的保真、回读、总成本与完成率联合测量 |
| Worker 崩溃哪些能续、哪些只能停 | 本地文件三种真实进程故障有明确恢复／未决结果；更多路径有离线测试 | P0：模型返回／Checkpoint 缺失、真实租约交接；远程副作用不得宣称已恢复 |
| 成功率、延迟、成本 | 历史报告已有分项用量、耗时和失败分母 | P1：重复稳定性、同条件对照、未知费用、误阻断；小样本不宣称稳定尾延迟 |
| 工具调用成功率 | Trial C 33/37，四次 context_read 失败有记录 | P1：按工具／错误类别对照，避免只报模型轮数下降 |
| 失败归因与回归 | 已有缺陷、修复和离线回归；RI-14 根因未确认 | P0/P1：保存故障窗口、主因／次级异常与可处置状态；修复后同任务复跑 |
| 旧 Worker 未停但租约已过期 | 本地 lease 身份／期限校验和迟到提交单测已有 | P0：跨进程交接证据；没有远端 fencing 就不承诺远端动作停止 |
| 外部副作用完成、结果未落盘 | 文件意图／后置条件对账及 SIGKILL 已有 | P0：每种工具分别定义证据与停止条件，不说通用 exactly-once |
| 模型成功、Checkpoint 写失败 | 现有遥测和失败处理，不是全局事务 | P0：专门故障注入；区分重复生成费用和工具重复副作用 |
| 取消到底停了什么 | Host 等待、提交保护与原生进程组终止是不同路径 | P0：按执行类型展示验证；已成功操作不自动回滚 |
| Event 能否重建、哪些另存、如何演进 | 业务聚合 reducer 与文件格式兼容路径已有 | P1：旧业务事件迁移、缺 blob、状态重放与禁止副作用的明确证据 |
| 术语多、技术取舍少 | 已有具体本地文件未决窗口、待确认变更与来源撤回设计 | P1：对外分别说明执行／上下文和持久化／恢复，各选核心设计、故障、验证；内部层名仅作定位 |

前一版“自动评分 + 72 次对照”的建议没有充分展开模型替换、连续压缩净收益、生产模型提交窗口、取消语义和事件演进；本计划将其补为独立验收项。最需避免的是用一个总分遮住这些不同问题。
