# 面向包装售前与跟单的业务数据

2026-09-18，按用户要求调整优先级：不继续用论文数量扩库。业务首先需要供应商与型号资料、结构/参数/测试条件、适用范围和待确认项。研究文献保留为辅助参考，新取得的两篇不进入默认业务库。

当前可用的是 **6 条产品系列目录**，不是 6 份供应商 TDS，也不是 6 个已确认可生产的型号。分别为 Constantia Flexibles 的 EcoLamHighPlus、EcoVerHighPlus，Huhtamaki 的 blueLite、blueloop PE，以及 Amcor 的 AmPrima Plus for coffee、AmFiber Performance Paper。来源定位见 [目录数据](../../src/manufacturing/coffeeProducts.ts)，每条包含供应商、系列名称、官方 URL、章节、可见版本标记或“未知”、资料形态与检查日期。

这些字段用来寻找资料与询问供应商。咖啡豆、咖啡粉与速溶咖啡采用显式分类，不能因同属咖啡而互相推荐。PE/PP 等检索标签也不是确认层序。厚度、OTR/WVTR、生产尺寸、具体阀配置、封口参数、报价、认证、订单适用地区均没有权威数值记录，参数数组为空，不用猜测补齐。

## Agent 如何读取

`packaging_find_products` → 服务端目录筛选 → 现有 KnowledgeStore → 有版本的证据 ID 和官方链接 → ContextEngine → 下一轮 Agent。示例：

```json
{"query":"EcoLamHighPlus 咖啡袋", "coffeeForm":"roasted_beans"}
```

返回的目录明确标记 `metadata_only`、`conclusionAllowed:false`，以及按具体型号、层序/厚度、阻隔测试条件、袋型/阀、封口匹配、地区/报告、储存期、商务条件划分的 8 组追问。`coffeeForm` 可为 `roasted_beans`、`ground`、`instant`；未知时应先问客户，不能自动推断。公共目录和私有版本仍经服务端权限校验；撤回、过期的记录不可被工具读取。

普通会话、Plan 与需求单阶段已登记该 Tool。选中的目录使用已有 `knowledge_selected`、证据选择版本和需求单来源链保存。目录能证明“这条线索从哪里找到”，不能证明某个生产参数成立。资料不足时继续追问。获准的供应商资料与人工确认仍是后续材料/生产决策的依据。

界面的“导入供应商产品目录”沿用持久导入队列；“按当前问题查产品目录”只查这些记录，不返回研究论文。记录详情标为“Packx 整理的目录记录（不是厂商原文）”，可以像其他证据一样选入当前任务。普通全文检索另保留为技术证据检索入口，混合模式可使用本地 Top-20 重排。

## 权限与维护

仅保存自编目录、事实性的产品名称、官方链接和原创追问，没有下载或向量化供应商网页/PDF 全文。`knowledge-import.v1` 的许可字段只覆盖 Packx 自编目录，明确不授予供应商原文的索引与再分发权。供应商网站许可不明时仍是元数据状态；Amcor 的使用条款限制网站复制，本次只登记入口。其他官网未找到清晰全文索引许可，继续待审核。

本轮通过官方页面识别资料，不批量爬站、绕过验证码、联系供应商或发送询价。另发现[喜金中文包装目录入口](https://www.shii-chin.com.tw/)，尚未下载或纳入在售型号参数库，需另核对条款与具体型号。后续增加资料的验收单位是“能支持一组业务问题的型号资料”，不是篇数或搜索排名。

目录版本 `coffee-products.2026-09-18.v1`，源文版本独立记录，未知保持 null。90 天后进入待复核的目录期限；实际供应商资料有效期未知，不将 90 天称为原文失效日期。更新时新建 manifest 版本；旧版本需要在 UI 显式撤回，已有来源链不会偷偷改指向。

## 接入与本机验证

当前数据位于默认业务根目录 `.blackx-data/knowledge/knowledge.sqlite`，目录 manifest 快照在其 `raw/` 下，6 条记录各 1 块。原有 5 篇研究 568 块保留，共 574 块。新下载的两篇仍在 `data/knowledge/coffee-open-v2/` 与隔离实验目录，业务库未导入。

停止正常 Host 后可重复运行：

```bash
npm run knowledge:connect-products
```

复用已有连接检查程序，在真实业务库和现有队列执行导入、重复导入、普通会话 Tool/ContextEngine 读取、选择、重启后读取，并额外检查混合检索的真实本地 rerank。回复由本机脚本 Provider 整理，只验证连通，不证明 LLM 或选材质量。运行结束释放临时 Host，再正常 `npm run dev`。本机演示任务为“产品目录连通验证（来源与缺口 / 本地测试回复）”。

本机配置已启用 `PACKX_KNOWLEDGE_RERANKER=local-mmarco`；清除后重启即可回退旧混合排序。其他模型配置没有改变，真实对话仍由用户自己配置的生成模型负责。该检查不调用付费模型、不发送客户消息。

实际[验证记录](../evidence/knowledge-overlap-rerank-verification-v3.json)包含正常 Host 查询、导入幂等、重启读取、ContextEngine 收到的证据 ID、本地真实重排用量与检查结果。初次接线暴露了会话/Plan 工具白名单遗漏，补齐后重新验证通过；历史失败保留。全量检查 65 个测试文件、366 项通过、20 项跳过；最后目录登记变更再通过 10 项相关测试与客户端/服务端类型构建。浏览器中也可读取演示任务的来源与缺口回复。

## 接下来应接什么资料

优先针对已选择的产品系列索取具体型号 TDS、含温湿度和方法的 OTR/WVTR 报告、封口与阀匹配条件，以及明确的企业内索引许可。原始 PDF/表格通过现有导入入口解析、审核，保留版本、页/表位置、原值/单位和未验证状态。再加入企业授权的历史需求单、打样记录和供应商确认记录；这些资料按租户隔离，不公开。

这些外部资料目前为 **0 份获准的供应商技术全文**，没有真实企业资料和员工验收。当前交付证明目录治理、业务工具接线和检索实验能力，尚不能声称已建成可独立选材的工业知识库。
