# Plan 模式与子 Agent

Packx 支持在聊天输入框上方切换“直接执行”和“Plan · 确认后执行”。已有会话默认直接执行。

## 使用步骤

1. 选择 Plan 模式，在输入框描述要完成的包装任务。规划使用 Enterprise Layer 从存储构建的任务上下文：按时间保留的用户原话、当前 Fact 的值/确认状态/版本/来源、阶段、待确认修改、Artifact 与全部相关附件索引。最近正式回复只作为非权威工作笔记补充，不再以“最近 8 条、每条 2,000 字符”决定关键输入。内容超限时明确拒绝，不静默丢弃约束。
2. Agent 只使用文件/文档读取工具，生成最多 4 项子任务。界面展示计划版本、每项目标和所需工具。
3. 核对计划。需要修改时，在输入框提交修订要求，生成新版本。旧版本不能继续批准。
4. 点击“确认 vN 并启动子 Agent”。聊天中的“同意”不会自动触发执行。
5. Host 顺序启动独立子 Agent，界面逐项展示状态和结构化结果。文件写入/删除仍需在现有文件审批卡片中逐次确认。
6. 可以暂停、取消，或恢复已确认且可恢复的计划。运行时先暂停，再切换模式。刷新页面或重启 Host 后读取持久状态继续处理；关闭网页不会取消任务。
   每个子任务结束时会检查是否达成目标。如果报告计划不可行或没有完成证据，停止后续任务并显示原因；点击“结合当前结果重新规划”生成新版本，核对后重新确认。
7. 计划完成后点击“将结果转为需求单草稿”。Host 冻结该计划的目标、原上下文、确认版本、子任务结果和执行来源；在右侧逐项核对字段，生成新版本，再单独审批和导出。没有普通聊天消息的 Plan 会话也可导入。

结果中的证据和限制来自子 Agent 报告，仍需核对。计划确认不验证业务事实，不批准最终生产交付物，也不自动授权文件变更。

## 执行范围

- 子 Agent 有独立 Session、目标和工具白名单，共享父会话的本机用户权限范围。上下文独立不等于独立文件系统或独立操作系统容器。
- 每个子 Agent 可以执行被计划列出且 Host 允许的文件读取、文档读取、文本写入/删除；没有递归派生、后台任务或定时任务工具。
- 首版顺序执行独立任务，不支持任务依赖图或并行写入。需要消费前一步输出的步骤，应作为一个子任务内部的工作处理。
- 每计划最多 16 个 Runtime 执行片；每片最多 4 次模型 Loop 迭代、8 次工具调用、12,000 输入 Token，超时 60 秒。重试不重置计划预算。此限制不是精确费用估算。
- 子任务结果汇总在计划面板中，按任务顺序保留摘要、证据与限制，不自动提升为已验证需求单。
- 显式导入只接受已完成的最新计划，且会话版本与附件索引未变。来源快照最多 32,000 字符，超限拒绝而非静默丢弃；导出保留来源计划版本。重新规划不会覆盖已导入的历史快照，主动导入新版本后沿用需求单的版本失效与重新确认规则。
- 需求单允许补充材料结构、材料厚度、印刷方式、表面工艺、封口方式和排气阀要求。这些属于待核对的需求信息，不代表已验证生产规格；填写后的补充字段也必须确认才能审批。

## 失败与恢复

来源或会话变化、过期版本、无效模型输出、工具拒绝/失败、预算耗尽都会停止推进。可重试 Provider 错误可以恢复；其余错误请核对已完成结果并重新规划。

### 重新规划检查点

- 子任务新输出必须包含 `assessment: { decision: "continue" | "replan", reason: string }`。执行者发现假设冲突、必要输入/工具缺失、无效依赖或目标不可达时报告 `replan` 并停止；不阻碍当前目标的普通不确定性仍放在 `limitations`。
- Host 在每个完成结果进入下一子任务或最终完成状态前检查 Schema、assessment 和证据是否为空。`replan` 或空证据形成 `plan.replan_required` 持久事件，状态为 `failed`，失败码 `plan_replan_required`，不允许直接 resume。执行结果、原因、Session、Execution、使用量保留在旧版本。缺失或错误的 assessment 以 `invalid_plan_assessment` 停止。
- 点击重新规划后，使用最新来源快照建立新版本，并记录 `replanFromVersion`。规划输入包含直接前一版本的失败、任务和结果节选及执行引用；完整历史仍保存在版本化存储。节选不是完整历史上下文，也不成为权威事实。修改输入框目标重新生成时，同样保留被替代版本的引用。
- 新版本只规划剩余或纠正工作，不继承审批；用户必须核对修订方案并确认具体版本。不会自动反复调用规划器或重置原版本的预算；同一任务最多 4 个版本（最多 3 次修订）、跨版本累计 32 个 Runtime 执行片；规划、失败尝试、恢复都计入总量，取消、切换模式和修改目标不能重置。仍保留每版最多 16 片的限制。
- 这是 Enterprise Layer 的确定性推进门槛与执行者自评，没有增加独立 Reviewer 或第二套 Agent Loop。证据非空和自评通过不证明语义正确、事实已验证或生产就绪；未被模型识别的计划问题仍可能漏过检查，需要用户及业务 Evaluator 核对。
- 旧数据库中缺少 assessment 的历史结果仍可读取；新执行及恢复后尚未提交的结果必须满足新检查，旧格式不会自动补成“通过”。

恢复同一版本不会重复执行已完成子任务。重新规划保留旧结果供核对，但新版本会按照新确认的任务执行，因此确认时需检查是否意外重复旧工作，特别是副作用不确定的操作。若进程在 Session 已保存、完成 Trace 未保存的极小窗口中退出，会报告 `plan_completion_evidence_missing`，需要人工核查，不会冒险重复文件操作。暂停规划阶段会取消该次规划，可以重新生成。

### ReAct 防循环与任务停止

- Agent Core 默认每片最多 32 次迭代、64 次工具调用；达到迭代上限返回 `slice_limit`，Runtime 保存 Session 并返回 `paused`，并非整个业务任务完成。Plan 收紧为每片 4 次迭代、8 次工具调用，每版本累计最多 16 个 Runtime 执行片，恢复不会重置计数。
- Runtime 有整轮超时（普通聊天 120 秒，Plan 每片 60 秒），工具按各自的 `timeoutMs` 超时；沙箱工具还有执行进程终止机制。
- Host 在工具调用前检测“同工具＋同参数”和周期 1～4 的重复动作序列，第三轮重复的最后一次调用会被拦截；对象键顺序和新调用 ID 不能绕过。工具连续失败 3 次即停止，同批次剩余调用不再执行。成功调用清零工具失败计数。
- 停止原因和动作摘要随 Runtime Trace 保存，同一 Turn 的恢复和重试不能清空已保存的计数或停止状态；不同用户消息属于新 Turn。后台队列保留不可重试分类。当前执行片被强杀时可能丢失尚未落盘的 Guard 状态，仍受 Plan 预先持久化的调用额度和队列上限约束。
- Plan 连续失败 3 次后停止恢复及重新规划，只有子任务通过检查点才清零，规划成功不清零。UI 展示累计版本、执行片和失败计数。触发总量或连续失败上限后，应先核对已有结果并解决原因，再明确新建任务。
- 该策略沿用 Runtime Adapter/Hook，没有修改 Agent Core。重复检测可能阻止合理轮询，不是语义正确性证明；超出检测窗口的循环由原有硬限制兜底。32 次调用预算不等于精确货币费用上限。详见 [ADR-0023](adr/0023-loop-guards-and-task-plan-budgets.md)。

## API 与存储

- `GET /api/conversations/:id/plan`：读取模式、修订号、计划版本和子任务结果。
- `POST /api/conversations/:id/plan`：提交 `mode`、`generate`、`replan`、`confirm`、`pause`、`resume` 或 `cancel` 命令。`replan` 仅接受最新、已停止或等待确认的计划，使用原目标和当前来源生成新版本。
- 每个命令带唯一 `requestId` 和当前 `revision`；操作既有计划时还需 `version`。确认还需 `confirmed: true`。
- 所有请求使用原有本地会话认证；身份由 Host 决定，不由模型或请求正文指定。
- 计划事件保存在 Agent 状态目录的 `plans.sqlite`；租约与执行片复用既有 Stage Job Queue。数据库应与会话、Trace、队列一同备份。

## 验证

`npm run eval:loop-safety` 验证重复动作、连续失败与正常进展的固定对照；`npm run eval:plan` 包含离线单 Agent 对照和固定不可行计划检查点评测：同 Provider、同预算，验证报告阻碍后停止后续任务、重新规划保留原因以及再次确认边界，不声称真实模型质量收益；`npm run eval:product` 包含真实本地 HTTP 编排验收，使用固定 Provider，不需要外部模型密钥。

`npm run dev:fixture` 也提供固定计划和两个子 Agent 的演示回复。它验证 UI 与编排链路，不代表真实模型读取或分析了资料。

架构、权限、迁移和收益边界见 [ADR-0015](adr/0015-confirmed-plans-and-bounded-subagents.md)。
