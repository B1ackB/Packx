# Packx CI 安全与合规建设计划

日期：2026-10-16。状态：本地配置与 macOS 本地验收完成；已获授权提交 CI 分支与 PR，实际远端运行待验证，平台设置待单独确认。负责人：仓库维护者。适用范围：当前包装行业产品与自研 Agent Runtime 的代码集成检查。实现与操作说明见 [CI 运行与验收](ci-operations.md)。

目标是在每次代码合入前，自动验证代码、离线行为、浏览器交互与 macOS 原生能力，同时限制 CI 的权限、数据接触面、供应链风险和费用。采用 GitHub Actions 与现有检查入口，按“可复现检查 → 远端验证 → 合并约束”推进。

本计划中的“合规”指遵守 [仓库约束](../AGENTS.md)、依赖与素材的许可要求，以及明确的数据处理和审批边界；不构成法律意见、认证或完整企业合规审计。真实客户资料如需进入云端，须另行确认合同、企业政策与数据处理要求。

## 2. 约束与安全目标

CI 属于仓库工程设施，不改变 Agent Core、Enterprise Layer 或 Domain Pack 的业务职责。遵守以下规则：

| 仓库规则 | CI 中的落实方式 |
| --- | --- |
| P0.1、P0.4 事实与生产精度 | 测试只使用合成事实与样例；通过 CI 不把模型输出升级为 verified 或生产就绪文件 |
| P0.2 危险操作受控 | PR 检查不发布、不部署、不发送客户、不修改权威业务数据、不自动合并 |
| P0.3 数据与 Secret 隔离 | 不注入业务密钥，不上传客户数据、个人记忆、业务数据库或真实模型轨迹 |
| P0.5 来源与许可 | 审查 Action、npm 依赖、浏览器下载及素材来源，固定版本，保留许可记录 |
| P2.1、P2.4、P2.5 | 保留离线恢复、幂等、权限和回归检查；失败有明确退出状态 |
| P2.6、P2.7 | 记录提交、工具版本、检查结果和必要日志；区分成功、失败、跳过、取消与基础设施异常 |

PR 代码、PR 标题、分支名、依赖包和上传产物均视为不可信输入。PR 测试必然执行候选代码，安全策略以“不给它业务权限和敏感数据”为基础，不能依赖候选代码自证安全。

## 3. 第一版工作流设计

使用一个工作流，包含三个执行 Job 与一个汇总门禁。正式验收时所有执行项均不可省略，不按修改路径跳过；先运行完整基线，再根据实际耗时决定是否精简。

| 稳定检查名称 | 运行器初选 | 内容 | 超时初值 |
| --- | --- | --- | --- |
| `core-offline` | `ubuntu-24.04` | 锁定依赖安装、供应链检查、`npm run check`、`eval:offline`、`eval:context`、`eval:recovery`、`eval:loop-safety`、`eval:memory`、`eval:m1`、`eval:m2`、`eval:plan` | 20 分钟 |
| `browser` | `ubuntu-24.04` | 锁定依赖安装、安装项目固定版本的 Chromium、`npm run test:browser` | 15 分钟 |
| `native-product` | `macos-15` | 锁定依赖安装、`npm run build`、`npm run build:native`、`npm run test:native`、`npm run eval:product` | 25 分钟 |
| `ci-required` | `ubuntu-24.04` | 等待上述三个 Job；以 `always()` 检查其结果均为 `success`，否则失败；不检出代码、不安装依赖、无 Token 权限 | 1 分钟 |

`ci-required` 是平台必需检查，不能自身按路径或业务条件跳过。它处理前置 Job 的失败、取消和跳过；整个工作流未运行或被取消时也不能满足合并要求。Job 内部的套件跳过另由执行数量与预期套件校验发现，不能仅依赖汇总状态。

以上运行器标签和超时是候选配置，须以实际可用性和首次远端结果校准。固定 OS 标签不能固定托管镜像全部内容，运行记录还需包含镜像与工具链版本。第一版不新增产品运行时依赖，也不引入自托管运行器。

触发规则：面向实际默认分支的 `pull_request`、该分支的 `push`，以及无业务参数的 `workflow_dispatch`。PR 检查使用平台提供的候选合并提交，并同时记录 PR head SHA、基准 SHA 与实际 checkout SHA。手动运行不替代 PR 对应提交的必需检查。只有启用 merge queue 时才增加 `merge_group`，避免队列缺少检查。[GitHub 事件说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group)

同一 PR 的新提交取消旧运行；不同 PR 相互独立。第一版不进行自动重试，不用 `continue-on-error` 或 `|| true` 隐藏必需检查失败。下载或平台故障可人工重跑，但保留原失败记录。

## 4. 权限与不可信代码隔离

以下均为计划采用的仓库策略：

- 工作流默认 `permissions: {}`；仅需要检出代码的 Job 授予 `contents: read`。不授予仓库写入、PR 写入、包发布、部署或 `id-token: write` 权限。
- checkout 设置 `persist-credentials: false`，不把检出凭据留给后续脚本。平台仍可能向 Action 提供受限 `GITHUB_TOKEN`，因此不能声称运行器绝对没有凭据。
- PR 检查不引用 Repository/Environment 业务 Secret，不使用 PAT、SSH 私钥、模型 API Key、云账号或生产数据库连接。
- 不使用 `pull_request_target`；不增加通过 `workflow_run` 接收 PR 产物并在高权限环境执行的链路。
- PR 标题、正文、分支名不直接插入 `run` 脚本。确有需要时通过环境变量或参数传递并正确引用，不使用 `eval`。
- 使用平台临时托管运行器，不挂载开发者目录，不连接公司内网，不复用本机 `.env`、业务状态或登录态。
- 第一版关闭依赖缓存及 setup-node 的自动包管理器缓存，避免引入跨信任边界的缓存复用；后续确需缓存时另行审查。

最小权限、输入注入防护及高权限触发器风险参考 [GitHub Actions 安全建议](https://docs.github.com/en/actions/reference/security/secure-use)。

Fork PR 的运行审批采用仓库可用的较严格设置；维护者先检查工作流、安装与构建脚本变更，再批准运行。批准运行不会使候选代码变可信，也不允许因此附加 Secret。[GitHub Fork 运行审批说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks)

## 5. 依赖供应链与许可

### 5.1 固定来源与安装行为

第一版仅使用必要的官方 Action。核对其原仓库、发布版本、实际提交与许可后，用完整 commit SHA 固定，并用注释记录对应发布版本；不使用浮动分支。实施时同时核对平台工作流依赖锁能力，适配成熟且无额外复杂度时优先使用，否则以完整 SHA 固定为基线。[GitHub 工作流依赖安全建议](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions)

npm 使用 `npm ci --ignore-scripts --no-audit --no-fund`；漏洞审计放入独立命名步骤，避免安装日志掩盖审计状态。包清单与锁文件不一致时失败，禁止 CI 修改锁文件、自动升级依赖或执行 `npm audit fix`。`--ignore-scripts` 限制安装生命周期脚本；后续显式运行的测试、构建及其依赖仍能执行代码。[npm ci 行为说明](https://docs.npmjs.com/cli/v11/commands/npm-ci/)

浏览器准备仅调用已安装、锁定版本的 Playwright，禁止临时拉取未知版本的 CLI。必要的系统依赖安装限定为官方浏览器安装流程，不运行网络下载后直接交给 Shell 的脚本。

### 5.2 漏洞与许可门槛

- 首次上线完整审计生产和开发依赖，建立实际基线，不预设当前零漏洞。第一版采用 `npm audit --audit-level=high`，未豁免的 high/critical 公告阻断合入；medium/low 登记处理。
- 审计服务不可用、响应损坏或执行超时必须标记失败，不视为“未发现漏洞”。审计会向 registry 提交依赖描述，核实 registry 来源；不混入业务内容。[npm audit 数据与退出状态](https://docs.npmjs.com/cli/v11/commands/npm-audit/)
- 逐项审查本次新增/更新的直接与传递依赖、Action、浏览器及测试素材的来源、许可和使用限制，补充 [依赖记录](dependencies.md)。未知许可或不明确的商业/再分发限制保持待审，不由模型确认合规。
- `npm audit` 不验证许可证、素材使用权或所有恶意代码。依赖与锁文件变更必须由维护者审阅；第一版不把一个包元数据字段当作完整许可审核。
- 优先修复漏洞。确需例外时记录公告编号、影响版本、实际暴露面、理由、补偿措施、负责人和截止日期；初始例外最长 14 天，由维护者明确接受，CI 只对精确匹配且未过期的条目放行。没有例外机制时直接阻断，不做整类忽略。

## 6. 数据、网络、日志与产物

### 6.1 数据准入

CI 仅从受审阅的 Git 提交检出代码。上线前检查被跟踪文件及测试实际加载路径；`.gitignore` 不会移除已经提交的数据，也不能防止错误的读取或上传配置。

禁止向 CI 引入 `.env*` 中的真实配置、`.blackx-data/`、`.packx-settings.json*`、客户文件、会话、个人记忆、模型请求/响应和本地历史实验目录。`.env.example` 只允许无真实凭据的示例。现有源码或证据目录中若含敏感资料，先停止相关数据进入 CI 的路径并处理，不能用“已在 Git 中”作为继续扩散的理由。

测试使用临时数据目录与合成 tenant/workspace/actor；不得连接真实企业存储。显式清除 `BLACKX_EVAL_BASE_URL`、真实 Provider 配置和业务路径覆盖变量，不使用加载本机 `.env` 的启动方式。产品 smoke 内部的回环 Fake Provider 与固定占位 Key 须明确标注为 fixture，不接入真实凭据。

增加版本固定、许可已审查的本地 Secret 扫描工具，首轮扫描当前受跟踪内容与可获得的 Git 历史，后续覆盖候选变更；报告只显示规则和位置，不输出命中值。豁免必须限定具体合成样例与原因。平台 Secret Scanning/Push Protection 可作为补充，先核实权限与套餐；工具选型与版本在实施阶段登记，不在计划中杜撰已完成扫描。

### 6.2 网络边界

安装阶段需要访问 GitHub、官方包源及浏览器下载源；漏洞审计需要 registry。检查清单列出这些用途，新增外部服务需重新审查。

运行测试不依赖真实模型或公网业务服务。浏览器沿用现有请求拦截；这只覆盖浏览器测试请求，不能证明所有 Node 进程完全断网。第一版的托管运行器也不构成网络白名单或硬性出站隔离。未来如必须处理保密数据，应先另行完成运行环境与网络隔离设计，不把数据迁入本流程。

### 6.3 留存与泄露处置

第一版不上传自定义 Artifact，不上传整个工作区、临时目录、浏览器 trace、模型轨迹或业务数据库。仅保留平台运行日志与必要的结果摘要；将仓库 Actions 日志留存设置为 7 天，实施时核实平台能力并读回确认。后续若增加失败截图或报告，只允许合成 fixture、明确路径和 7 天留存，并单独审核上传 Action。

日志只记录提交 SHA、工作流版本、OS/Node/npm/工具链版本、测试数量与失败摘要；不打印完整环境变量、凭据配置或敏感请求正文。GitHub 自动遮盖不是数据泄露防线。例外与安全验收证据按需脱敏留在受版本管理文档中，不能依赖短期运行日志作为长期审计档案。

若发现疑似泄露：停止受影响任务，限制日志/产物传播，由维护者处理撤销和轮换凭据，记录影响范围、清理与复验。删除日志不能替代凭据轮换。

## 7. 合并治理与费用

执行检查及 `ci-required` 均在远端出现并验证失败阻断后，再配置默认分支规则：要求 PR、要求 `ci-required` 成功、要求与基准分支同步、禁止强推与删除、要求解决评审对话。可用时限定检查来源为 GitHub Actions，禁止 CI 自动创建审批或自动合并。[GitHub 分支保护说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

只有一位维护者时不强制不可满足的“另一个人批准”；在有独立审阅者后再配置审批数与 CODEOWNERS。当前阶段由维护者重点审阅 `.github/`、包清单/锁文件、构建脚本和安全规则变更，并明确单人审核的局限。仓库内自检可被同一 PR 改写，不能替代平台分支规则与可信维护者审阅。

上线时核实管理员是否可绕过，尽可能限制常规绕过。紧急例外由维护者记录原因、提交、失效时间及恢复步骤；禁止把临时关闭检查保留为默认设置。套餐或权限无法落实某条控制时，明确列为缺口，不声称“保护已生效”。

费用控制先采用超时、取消过期 PR 运行、固定三个执行 Job 与一个短时门禁、无付费模型、无自动重试。维护者依据实际套餐核对 Linux/macOS 分钟消耗及预算上限，再启用可用的费用限制；不预设免费额度，也不承诺零费用。目标耗时为 PR 总墙钟时间 15 分钟以内，属于测量后的优化目标，不能据此跳过安全检查。

## 8. 实施顺序与交付物

| 阶段 | 工作 | 交付物与退出条件 |
| --- | --- | --- |
| A 基线确认 | 只读核对远端、规则、权限、费用；检查已跟踪数据；核对另一个工作树的草稿；隔离无关改动 | 来源清单、实际检查矩阵、数据准入结论及差距记录。发现敏感资料先处理再推进 |
| B 本地实现 | 复用草稿中的已验证思路，按本计划实现三个 Job；补充 Secret 扫描、漏洞门槛与必要策略校验 | `.github/workflows/pr-checks.yml`、必要的最小安全检查入口、依赖记录及运行说明；不加入部署或模型密钥 |
| C 本地验证 | 在干净的候选提交上验证安装与脚本、YAML/工作流语法、权限和下面的负向场景 | 记录实际结果与 skip 原因；本地成功只证明本地配置/脚本，不表示远端已通过 |
| D 远端验证 | 审阅明确文件清单后提交 PR；观察三个 Job、Fork 策略、取消与失败结果 | 对应候选提交的实际运行 URL、SHA、结果及脱敏证据；缺失或全跳过的必需检查不能验收 |
| E 启用合并约束 | 依据实际 check 名配置平台规则，验证失败不能合入，修复后可合入 | 平台设置读回结果、安全验收记录、维护与故障处理说明 |

建议阶段 A 至 C 预留 1 至 2 个工作日，阶段 D 至 E 预留半天至 1 天；这是计划估算，供应链历史缺口、运行器差异或平台权限问题另计。正式提交或更新 PR 前，获取实际 upstream 并确认候选包含最新基准；若基准移动，同步后重跑相关检查。

用户已于 2026-10-16 授权先实施本地配置和验证，保留所有无关改动；提交远端和修改 GitHub 设置前必须再确认。阶段 A 至 C 已完成；用户随后明确授权仅提交 12 个 CI 文件、同步最新主分支、验证后推送新分支并创建 PR。GitHub 设置仍须在远端 CI 跑通后单独确认，未授权部署、发布或额外消费。

## 9. 安全验收与完成标准

负向实验使用临时合成内容，不使用真实 Secret，不向外部地址发送测试数据。涉及运行恶意代码或改变平台设置的验证必须在受控分支/测试环境中进行，不影响真实业务。

| 场景 | 预期结果 | 所需证据 |
| --- | --- | --- |
| 干净检出与锁定安装 | 不依赖本机未提交文件、缓存或业务配置 | 实际 checkout SHA、安装结果与版本 |
| 故意破坏类型或断言 | 对应 Job 失败，PR 无法合入 | 失败运行与保护规则的阻断结果 |
| 原生测试被整体跳过 | `native-product` 验收失败；必须证明真实沙箱测试执行且数量非零 | 运行器、启用条件、预期套件清单与执行结果 |
| 安装脚本或锁文件漂移 | 生命周期脚本未执行；锁文件不一致导致安装失败 | 临时合成包/清单实验，不污染生产依赖 |
| 新增敏感文件或测试凭据样例 | 扫描拒绝，日志不回显命中值 | 扫描正反例与报告位置 |
| High/critical 公告或过期豁免 | 未获有效精确豁免则失败；审计服务故障也失败 | 固定审计响应 fixture 或可控故障验证 |
| 工作流扩大权限或改用危险事件 | 策略检查拒绝；维护者能在 PR 中识别 | 变更反例、审阅要求与平台权限设置 |
| PR 标题含 Shell 特殊字符 | 标题不进入脚本代码，不产生额外执行 | 配置审查；如处理标题则用无害标记实验 |
| Fork PR | 审批策略符合预期，无业务 Secret/写权限；不为完成实验开放额外权限 | 平台策略读回；具备受控 Fork 时补实际运行证据 |
| 同一 PR 推送新提交 | 旧运行取消，新 SHA 重新检查，旧成功不能代替新检查 | 两次运行的 SHA 与状态 |
| 缺失、取消、失败或跳过的必需 Job | 均不能作为完成证据；验证平台不能误放行 | 实际结果与合并阻断证据 |
| 留存与上传 | 无自定义产物；日志留存符合 7 天目标 | 平台设置读回与首轮日志人工抽查 |

工作流语法/策略检查需针对真正的 YAML 结构与 Job 权限判断，不能只用字符串匹配；工具必须固定版本并纳入供应链记录。仅保留上述控制所需的最小校验，不新建通用 CI 框架。

只有以下条件全部满足，才能标记“CI 基线已上线”：三个执行 Job 及汇总门禁在实际远端成功；预期核心与原生测试确实执行；关键负向场景阻断有效；平台权限与分支规则读回确认；依赖与数据准入记录完整；无未披露的豁免或能力缺口；运行与故障说明可复现。受限环境无法执行的验收保留为待完成，不能用静态配置检查替代。

## 10. 维护与回退

维护者按月检查固定 Action/工具版本、漏洞、许可变更与费用；依赖或工作流变更时重新审查对应信任边界。可在另行确认后引入依赖更新 PR，保持人工审核与 CI，不自动合并；本计划不创建定时任务。

普通 CI 缺陷通过 PR 修复或恢复到最后一个已验收的工作流提交，重跑后再合并。运行器/registry 故障标记为基础设施异常，不通过删除测试、全局忽略漏洞、增加 Secret 或扩大权限来“修绿”。工作流回退涉及 check 名称变化时同步审查平台规则，避免保护失效或所有 PR 卡死。

暂不建设自动部署、制品发布、签名、真实模型在线评测、自托管运行器、复杂跨平台矩阵或通用安全平台。未来确有发布或保密数据需求时，单独设计权限、审批、幂等、审计与回退，不直接扩权现有 PR 流程。
