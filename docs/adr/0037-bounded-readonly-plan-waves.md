# ADR-0037：单图租约下的有界只读并行

日期：2026-10-19。状态：Accepted，已完成本地实现与验证。发布阶段已获本批文件的提交、推送和 PR 授权；合并与部署未授权。实际远端 CI 以对应 PR 检查为准。

## 背景

PR #53 的 main `972266e4bdcef83f7d054afdcbd98ae18a4c21b0` 已有四节点串行 DAG、独立 worker Session、版本确认、来源复核、持久队列及完成记录恢复。产品负责人授权本地推进互不依赖只读任务的有界并行，要求故障路径和同预算基线；不授权付费模型、并发写入或代码执行。

检查发现 `StageJobScheduler.runNext` 全局只执行一个 job，`PlanVersion.activeTask` 只能描述一个节点。直接并发旧执行方法会共用陈旧状态、缺少预留和尝试身份。落点属于 Enterprise Layer；Core、Provider、文件权限和网络读取器不变。

## 决定

1. 保留一个计划 Queue job 和它的排他 lease。一个执行片从确定性就绪集合中最多选择两个节点，同批结束后 checkpoint，让其他 queued job 获得调度机会；依赖节点在下一片启动。不同图不同时执行。此为批次调度，不引入节点独立 Queue job、公平性服务或分布式调度。
2. Host 在提出计划时，仅对**全部节点工具均属于既有 readTools 白名单**、且至少两节点的计划保存 `readConcurrency: 2`，确认前 UI 明示。包含任一写工具的整图保持串行；旧计划缺省继续串行。执行前重新校验白名单，权限收紧时停止。规划器不决定并发权限。
3. 每个节点最新尝试保存 `taskIndex / attempt / generation / jobId / leaseId / sessionId / idempotencyKey / status / startedAt / failure`。状态为 `running → completed | paused | failed | interrupted`；旧尝试的转换保留在 SQLite 追加事件中。就绪/等待由 DAG 与成功收据计算。`children` 以 taskIndex 关联，可按完成顺序追加，展示及下游输入仍按已确认索引/声明边路由。
4. 节点共享父图租约，提交必须通过 Queue renew fence、版本/代次、当前尝试及来源复核。租约保护整个图，节点无需独立续租：父租约丢失时所有节点失去提交资格。相同 lease 的重复处理不能接管运行中的 reservation。批次取消信号传播到每个 Runtime；各节点另外有 60 秒截止时间。不可合作的 Adapter 的迟到响应被观察但不得提交。
5. 开始实际 Runtime 调用前，SQLite 同一事务持久化节点尝试并增加 `calls`；跨版本/每版本预算从最新状态检查。剩余一个槽时只准入一个节点。每片最多四次 Loop 迭代、八次 Tool、12,000 输入 Token；失败、取消或响应不明不退还调用槽。它们是执行量限制，**不是精确模型调用数、Token 账单或货币硬上限**。
6. worker Session 独立，重试或未完成尝试使用新 Session/key，旧进程不能覆盖新尝试。Runtime 主动 checkpoint 的已暂停节点继续原 Session/key。下游只收到已声明直接上游报告，没有兄弟消息历史。并行 worker 强制 `read-only / approvalPolicy=never`；来源、报告、节点输出仍是未验证数据，不增加权限、确认 Fact 或批准交付。
7. 任一节点失败立即停止该批和后续任务；已完成收据保留，其他运行尝试记为 interrupted。只有原有可重试分类允许用户恢复；来源改变、格式错误、缺完成 Trace 或 replan 等需要人工核对/重规划。暂停、取消、会话删除、来源改选和撤回维持现有失效边界。
8. 保留队列 `maxFailures=1` 的保守语义：进程崩溃后租约过期成为 dead letter，reconcile 将计划置为可恢复失败，**不自动重发未知模型请求**。用户恢复新代次后先按保存的 Session/key 核对完成 Trace：已有合法完成结果零新增调用地接回；无完成结果的只读工作可在已预留消耗之外再次扣槽重试；有最终 Session 但无完成 Trace则停止。已提交节点永不重跑。

## 替代方案和取舍

- 不改、继续串行：保留为旧计划/写入计划基线，但不能验证独立读取的重叠。
- 直接 `Promise.all` 旧 worker：缺少尝试状态、共享预留、上下文和租约提交约束；不采用。
- 节点独立 job、可配置通用线程池、跨图公平调度：会触及所有 Stage Worker 的并发/资源语义。当前最多四节点、单图执行可用父租约覆盖全部提交边界，先不扩大执行平面。
- 任一完成即动态补位：能进一步缩短非对称任务关键路径，但增加协调复杂度。当前批次会等待本批最慢节点；只有真实任务的延迟/资源证据证明收益后再改。
- 精确费用 reservation：Provider 缺少可靠统一报价/最大输出/重试与不明费用合同。保留已说明的执行量限制，不把它命名为费用硬上限。

这按 P1.9 复用 Port/Adapter 和现有队列，不扩展 Agent Core。P3.2/P3.3 的证据限于同图、同固定 Provider、同执行片预算对照；它支持此有界调度机制，不解除真实模型质量与真实用户价值的后续 Gate。

## 迁移、回退和退出条件

停机升级，保留 Session/Trace、plans.sqlite、队列、Artifact 和来源的一致备份，不改用户现有数据。旧计划保持串行；新计划在用户确认前固化只读并发合同。新字段不能交给旧二进制混跑或忽略后执行；旧实现不认识尝试 Session/key，可能重复未完成工作。回退先停止新增计划、暂停/排空任务，并保留兼容读取器；禁止删除并发字段、改写历史、丢弃来源版本来伪造兼容。

如果真实任务中批次等待、额外调用或人工恢复成本超过收益，停止为新计划设置 readConcurrency，保留当前版本的恢复和历史读取。只有同任务/同总预算的真实评测通过后才考虑节点 job、跨图并发；并发写入、任意代码、OS 级多 Agent 隔离另设 ADR 和验收。

## 验证和未验证

见[本阶段验收与演示](../evidence/readonly-parallel-2026-10-19.md)。固定对照验证输出/调用量一致且独立来源请求确实重叠；故障测试覆盖依赖等待、部分失败、取消/暂停、超时、重复派发、租约丢失、完成窗口对账、来源撤回、最后预算槽。真实 Host HTTP 使用本机固定 Provider，包含运行中 SIGKILL/重启/恢复，不能作为真实模型、用户价值或公网正向读取的证据。
