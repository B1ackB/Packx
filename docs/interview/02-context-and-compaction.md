# 02｜上下文工程与压缩深挖

[返回总入口](README.md)。主依据：[上下文管理](../context-management.md)、[ContextEngine](../../src/agent/context.ts)、[AgentLoop](../../src/agent/loop.ts)、[摘要器](../../src/agent/summarizer.ts)、[任务上下文](../../server/enterprise/taskContext.ts)、[Runtime](../../server/runtime/agentRuntime.ts)、[回读工具](../../server/runtime/contextRead.ts)。对应集成测试为 [contextLifecycle.test.ts](../../server/runtime/contextLifecycle.test.ts)。

## C01．你说的上下文工程是什么？和写 Prompt 有什么不同？

**回答：** Prompt 是其中的指令部分；上下文工程还决定本轮放哪些数据、来自哪里、是否最新、权限是否有效、多少预算、如何保留证据，以及中断后如何重建。Packx 把输入视为从持久化状态编译出来的受限视图。

**深挖：** 同一句提示词，用旧 Fact、撤回资料或混入另一个任务的历史，结果仍可能错误。我的解释会先说数据生命周期和信任边界，再说提示词组织。把“不要幻觉”写进 system 不能代替版本校验和权限检查。

## C02．为什么分开 transcript、messages、taskContext？

| 对象 | 用途 | 谁决定内容 | 是否可以用摘要替换 |
| --- | --- | --- | --- |
| `Session.transcript` | 用户原话、正式助手回复与 UI 历史 | 持久会话逻辑，稳定消息 ID | 不可以 |
| `Session.messages` | 模型工作历史、工具调用／结果、摘要与回执 | Runtime／ContextEngine | 非必留部分可以 |
| `taskContext` | 当前目标、Fact／Stage／Artifact／Approval、来源及偏好 | Host 从存储构建 | 不由模型摘要改写 |

**回答：** 它们分别解决可追溯交互、有限推理工作区和当前权威业务状态。只存一份 messages，压缩就可能同时破坏 UI 历史和业务证据；只保留所有历史，又容易超过预算并引入旧状态。

**深挖：** transcript 是交互证据，不代表其中每句话都是正确业务事实。助手旧回复也不天然可信；启用个人记忆的 Host 会清空 taskContext 的派生 workingNotes，避免旧偏好从回复里回流。

## C03．taskContext 具体怎样构建？

**回答：** `buildTaskContext` 接收当前 scope、完整用户原话、事实投影、事件、附件和知识选择。输出有顺序的用户请求、当前 Fact 的值／状态／版本／来源、阶段、完成事件、未确认项、失效来源、待确认修改及 Artifact／Approval，再序列化并生成 SHA-256 binding。

**深挖：** 构建器先核对 scope，只接受当前 Run 或明确关联的业务 Run。内容超过 64,000 字符停止；Plan 输入另有 32,000 字符上限。当前实现主要是确定性拼装，不是模型判断哪些需求“值得记住”。因此保留完整约束更可靠，但长任务会触及容量上限。

## C04．很早以前用户说的“不要 PVC”，压缩后会不会丢？

**回答：** 当前任务上下文保留按顺序排列的用户原话，不只取最后几条。它作为 durable／pinned 的任务数据进入请求，压缩不能悄悄删掉。原始 transcript 也另存，必要时可以回读。

**深挖：** 这不等于模型必定理解或遵守否定条件。Host 能确定保留了文字，语义遵循仍需真实模型评测。全量原话越来越长时，当前策略会显式停止并要求拆分或处理旧约束；没有自动准确判定任意自然语言约束何时失效的机制。

## C05．用户先说一万，又说一万二，哪一个优先？

**回答：** 当前业务参数以存储的 Fact 版本和确认状态为准；用户原话按顺序呈现，更正是需要处理的输入。如果新 v2 未确认，而旧 v1 确认过，taskContext 会同时说明当前待确认 v2 和旧确认 v1，不能悄悄回退旧值，也不能自动确认新值。

**深挖：** 文本中“后来的明确更正优先”是上下文解释规则，不是完整自然语言冲突解决器。若新请求要求改变权威 Fact，必须走记录新版本／确认流程。若冲突还不明确，提问澄清而非靠摘要抹平。

## C06．taskContext.binding 和 historyBinding 有何不同？

**回答：** taskContext.binding 绑定当前完整任务输入，防止恢复或执行过程中继续使用旧事实／来源。historyBinding 绑定工作历史所依赖的个人记忆有效视图，判断旧 messages 和快照是否仍能使用。

**深挖：** 前者更像“这次执行的业务输入有没有变”，后者更像“这段派生历史是否基于仍有效的偏好”。普通新消息会改变任务输入，不必等同全部工作历史失效；撤回偏好即使未改变 Session revision，也必须让 historyBinding 变化。细节见 M10。

## C07．当前上下文输入预算怎样计算？

**回答：** 硬上限为 `min(应用输入上限, 模型上下文容量 − 输出预留 − 安全余量)`。当前应用默认配置是 131,072 容量、4,096 输出预留、8,192 安全余量、100,000 输入上限，所以默认主请求硬上限为 100,000 Token；具体任务可以更低。

**深挖：** 这些是应用策略，不是配置模型的官方规格。必须核对实际模型。工具定义、输出 Schema、协议字段和加载图片也占输入；只统计聊天文本会漏算。容量预算不等于货币预算，价格未配置时费用不能当零。

## C08．Token 怎样数？Provider Count 失败会改用估算吗？

**回答：** Provider 提供 countTokens 就优先调用；未提供时才用 UTF-8 字节数／3，加每消息协议和已加载图片余量进行估算。已经配置的 Count 请求失败会暴露错误，不能静默退回估算掩盖异常。

**深挖：** 启发式不是 tokenizer，没有实测误差上界。图片默认每张计入 4,096 余量，也不代表真实模型视觉计费。Provider 返回值还需要是非负安全整数，防止负数、NaN 或错误 JSON 让预算失效。依据：[tokenBudget.ts](../../src/agent/tokenBudget.ts)、[Provider 校验](../../server/anthropic/client.ts)。

## C09．什么时候触发压缩，为什么压到 45%？

**回答：** 默认输入估算达到硬上限的 70% 触发，45% 是目标，用来留出接下来工具调用增长的空间。无 Provider Count 时还保留 ContextEngine 的字符阈值触发。目标不构成保证，压完必须重数，仍超硬上限就拒绝。

**深挖：** 当前由 Token 比例换算目标字符数，是工程近似而非最优装箱或动态质量策略。70%／45% 不是已经证明最优的参数。可比较不同阈值的保留率、额外摘要调用、任务成本和完成率，但当前不能宣称做过全面调参。

## C10．压缩的真实执行顺序是什么？

**回答：** 工具输出阶段先归档大正文并形成可回读引用；需要压缩时先把较早且可回读的工具正文换成引用，再按消息单元保留必留内容和近期内容；被移除内容存原文快照，再生成带来源／覆盖信息的未验证摘要；最后对整个请求重新计数。

**深挖：** 架构原则中的“外置、清理、状态快照、近期内容、摘要”是优先顺序，不应描述成已经实现了一个能语义淘汰任意过期自然语言事实的引擎。当前精确保证来自 pinned、消息组、binding、来源验证及预算检查。

## C11．工具调用与结果为什么不能独立删除？

**回答：** 一条 assistant 消息可能同时发出多个 toolCalls，后续 tool 消息通过 ID 对应结果。ContextEngine 把调用消息和相邻匹配结果作为一个单元，成组保留或移除；结果未齐全的单元必须保留，组内任一 pinned 也保留整组。

**深挖：** 否则模型可能只看到结果却不知道问题，或看到悬空调用；Provider 协议也可能拒绝。注意两个层次：工作历史裁剪按工具组保证配对，**摘要器输入按完整消息分批，不额外承诺每一批都包含完整工具组**。现有部分文字把两者都写成“消息组”容易误读。

## C12．哪些内容是必须保留的？如果它们已经超限？

**回答：** 稳定策略、选定 Skill、当前输入、durable 任务数据、需要保留的回执、未完成工具组等进入 mustKeep。Loop 会连同工具定义／Schema 检查必留输入；它们本身超限就返回 `budget_exceeded`，不会删硬约束换取成功调用。

**深挖：** pinned 的生命周期有区别：新轮 compile 不会永久保留所有历史 pinned，只有 durable 或恢复中仍需 pinned 的消息继续保留。否则每轮都固定历史会让压缩失效。停下来不代表“系统没有能力”，而是准确承认当前任务不能在约定预算内可靠表达。

## C13．摘要器具体如何分批，预算多少？

**回答：** `ModelContextSummarizer` 按完整消息组织批次，保留目标、否定、单位、条件、失败和来源。默认一个执行片最多 4 次生成、单次输入 6,000、输出 512，累计输入加预留输出不超过 26,048 Token；Count 调用最多为生成额度的四倍，即默认 16 次。还受当前任务更低预算限制。

**深挖：** 调用次数和累计分配在摘要器实例内保存，同片多次压缩不重置。单条过大、Count 后超预算、累计预算不够时不截尾冒充已处理。这里预算限制的是调用分配，真实 Token／费用还要看 Provider usage；新执行片的摘要预算与 Plan 跨片预算是不同层。

## C14．`INCOMPLETE` 究竟意味着什么？

**回答：** 摘要记录 sourceMessages、coveredMessages、调用数、实际覆盖区间和原始 sourceRef。只要并非全部源消息被合法摘要，就标 `INCOMPLETE`。超长单消息被跳过、输出为空、模型返回工具调用或超输出预算，都不能计为已覆盖。

**深挖：** coverage complete 也只是“这些消息进入了可接受的摘要结果”，不保证每个语义细节都正确。模型有可能遗漏一个否定词，所以还要保留当前结构化任务状态与可回读原文。不能把 `complete` 报成摘要准确率 100%。

## C15．为什么不直接截断工具 JSON 或长摘要？

**回答：** 截断会破坏 JSON、丢单位、断开条件，甚至把“不适用”截成“适用”。Runtime 把完整工具正文保存为不可变快照，返回完整引用封套；摘要输出不符合预算时不接受其覆盖，而非切掉末尾装成完整结果。

**深挖：** 外置降低热上下文成本，却增加回读与来源验证成本。源快照写入失败必须阻止继续，否则只剩一个无法解析的引用。工具通用输出契约还不完全统一，不能宣称任意工具都已自动具有完整领域证据语义。

## C16．`context_read` 怎样读回大结果？

**回答：** 通过 sourceRef 选快照，offset 分页；messageIndex 选择消息，jsonPointer 进入大 JSON 的某个数组／字段，再按完整记录或完整行返回。响应包含 total、truncated 和 nextOffset。当前同一工具限制在绑定的 tenant／workspace／run／session。

**深挖：** 一个不可分记录超过页预算时返回 `single_unit_exceeds_budget`，要选更细字段或专用源工具，不将半个值当证据。启用 historyBinding 时，transcript 回读仅暴露用户消息，完整助手历史仍可在 UI 查看。分页成功也不代表资料整体已经读完。

## C17．为什么引用要带 hash、版本和权限验证？

**回答：** 一个路径或 ID 只能定位对象，不能证明内容还是当时那一版、当前仍有权限。文档续读重新检查 hash 和授权；知识读取检查生命周期／有效期／权限，并保留证据 ID、内容 hash、位置、单位和条件。

**深挖：** hash 一致只证明字节一致，不证明内容真实或适用于当前订单。权限有效也不证明能合法重新分发。图像同样以引用持久化，加载时校验元数据与 hash，不能把历史所有图片默认重新发给 Provider。

## C18．摘要间接引用的来源撤回，如何防止继续使用？

**回答：** summary 的 readDependencies 指向原文快照。恢复和回读递归校验这些依赖，调用原 sourceTool 的 validator 检查当前权限、内容和状态；快照不存在、校验器缺失、来源变化就停止。最多访问 128 个不同快照，超限要求重建。

**深挖：** visited 集合避免重复遍历和依赖环造成无限工作。普通 contextBinding 变化的历史快照可能标 stale 并作为历史未验证数据阅读；**historyBinding 不匹配则直接拒读**。两种规则不能混说成“所有旧快照一律删除”。这也不构成通用实时撤回已发送给 Provider 的内容。

## C19．为什么完成一个 Tool batch 就保存 checkpoint？

**回答：** 这样恢复从协议完整的边界继续，已经有调用及结果的工具不必从零重走。Checkpoint 保存 turnKey 和 task context binding，Session 用 revision CAS 防止覆盖新状态。

**深挖：** 工具副作用到 checkpoint 落盘之间仍有窗口，所以工具账本必须独立；不能只靠消息历史判断做没做过。只读工具在某些崩溃窗口可能重读，写工具则根据成功／未决记录去重。checkpoint 是恢复位置，不是事务提交全部副作用的证明。

## C20．原始历史如何迁移，旧系统丢掉的对话能恢复吗？

**回答：** v1 迁移只保存实际仍存在的用户原话和正式回复，确定性补齐消息 ID，标 `legacy_partial`；首次写 v2 前保留原 v1 JSON 备份。旧摘要与没有来源验证元数据的工具正文不能直接变成可信新历史。

**深挖：** 已丢失原文不能用模型补造。`kind=dialogue` 显式标记原话，避免用户引用摘要前缀时被误当内部摘要隐藏。升级与回退要有一致数据备份，旧程序不能继续写新格式。依据：[state.ts](../../src/agent/state.ts)、[文件会话存储](../../server/runtime/fileAgentStateStore.ts)。

## C21．模型报 context window exceeded，会怎么处理？

**回答：** 第一次窗口错误允许再压缩一次，只有实际移除了内容且重数未超预算才再尝试；最多两次主生成尝试。第二次仍失败就退出，不对所有模型错误做循环重试。

**深挖：** 本地估算误差或配置错误都可能导致 Provider 拒绝。窗口错误在 Runtime 最终可归为 `budget_exceeded`。反复扩大预算或删权限策略都不是合法恢复。摘要调用本身也可能失败，因果链决定最终分类，不能说所有摘要问题都最终是 context_failure。

## C22．压缩是否真的降低费用？当前有什么证据？

**回答：** 本次固定对照中，候选工作上下文估算从 34,313 降到 4,355 Token，保留 4 条指定约束、2 个引用和当前 Fact 版本。但候选多了摘要生成及计数调用，且使用 Fake 和字节估算，不能据此宣称真实费用下降某个比例。

**深挖：** 比较旧方案也要报告：旧方案最终 4,057，比候选更小，但丢了指定约束／引用。压得最短不一定最有价值。总成本应包括主生成、摘要、计数、缓存命中、失败重试和人工返工；语义／计费收益需同模型、同任务、相同预算的真实对照。

## C23．你实现了 Prompt Cache 吗？和 memory 有关系吗？

**回答：** 当前记录 Provider 返回的缓存读／写统计，没有新增缓存优化系统。Prompt Cache 是 Provider 重用计算的能力；个人记忆是应用明确保存并召回用户偏好；压缩则改变模型工作输入。三者不同。

**深挖：** 即使未来稳定前缀提升 cache 命中，也不能缓存旧审批或无视来源撤回。未知缓存用量要保持 unknown／null。没有测量真实请求就不能把“理论上可缓存”写成项目性能成果。

## C24．如果继续改进上下文系统，你先做什么？

**回答：** 先冻结真实长任务样本，检查否定条件、单位、冲突、当前版本和引用在多轮压缩后的保留及实际遵循，再定位最大失败来源。可能的改进包括显式约束变更确认、超大源内容更细粒度读取、预算估算校准和受控保留期。

**深挖：** 这些是下一步建议，不是当前实现。无需一开始就加摘要层级、向量记忆或另一个监督 Agent。任何新压缩／选择策略都应同时评价质量、成本、恢复和撤回行为，避免用 token 降低掩盖证据丢失。
