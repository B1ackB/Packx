# 01｜架构、业务状态与完成证据

[返回总入口](README.md)。本篇依据：[架构原则](../architecture/principles.md)、[ProposalRunEngine](../../src/enterprise/proposalRunEngine.ts)、[业务契约](../../src/enterprise/contracts.ts)、[Runtime 契约](../../src/runtime/contracts.ts)、[Host 装配](../../server/index.ts)、[需求单 Worker](../../server/manufacturing/requirementBriefWorker.ts)。

## A01．项目解决什么问题？为什么需要 Agent？

**回答：** 包装售前的输入分散在对话、附件和技术资料中，且经常缺字段、互相冲突或发生修改。Packx 用 Agent 理解非结构化输入、选择资料和工具，再形成 `requirement-brief.v1`。系统保存每项信息的来源、确认状态和版本，帮助用户补齐、核对并批准需求单。

**深挖：** Agent 的价值是阶段内探索路径可变，不是把审批也交给模型。固定业务门槛用程序更可控；例如数量没有确认时，模型即使觉得“很合理”也不能批准需求单。是否减少售前时间、返工率和漏项，要靠真实用户任务验证，目前不能用离线测试替代。

## A02．三层架构分别负责什么？

**回答：** Core 提供行业无关的 Loop、Context、Skill、Hook、Provider 和 Tool 协议；Enterprise 管 Run／Stage、Fact、Artifact、Approval、Evaluation、事件、队列和恢复；Domain Pack 管包装字段、材料参数及适用条件等行业规则。

**深挖：** 判断归属看“换行业后是否还成立”。Token 预算属于 Core；个人偏好的确认和 actor 范围属于 Enterprise；OTR／WVTR 的单位与试验条件比较属于 Domain。企业层通过 `AgentRuntimePort` 调用 Runtime，不能依赖厂商消息结构。目录只是导航，最终以依赖和责任为准。

## A03．RunEngine 和 Runtime 为什么不能合在一起？

**回答：** Runtime 管一次阶段执行中的模型／工具循环，输出完成、暂停或失败。RunEngine 管业务阶段能否推进，它需要版本新鲜度、评价和审批等证据。两者生命周期不同：Runtime 可以完成一次询问缺失信息的回复，但需求单仍未完成。

**深挖：** Runtime 的 `completed`、Job 的 ACK、Stage 的完成是三种不同判定。将它们合并会让一句“已完成”绕过业务门槛。反过来，Runtime 达到执行片上限可以 `paused`，让队列保存 continuation；不能把暂停报为整个业务失败或成功。

## A04．为什么自研最小 Core，而不全部用框架？

**回答：** 项目需要明确掌控执行片、工具账本、上下文来源、检查点和业务恢复边界，所以保留一个较小的通用循环，把 Provider、原生解析和存储接在接口外侧。这里的收益是行为可检查、可做故障回归，不是声称自研全面优于现有框架。

**深挖：** 代价是协议适配、安全、压缩、恢复测试都要维护。新增需求先看能否用配置、Skill、工具或 Adapter 解决，再考虑 Core 扩展；关键边界变化要 ADR 和固定 Eval。可以把 Port 作为替换点，但“存在接口”不等于不同框架已经验证可互换。

## A05．沿一次“生成需求单”讲完整调用链？

**回答：** 用户提交对话／附件／选定证据，Host 读取当前状态构建任务上下文；企业层记录执行意图，经 Outbox 入队，Scheduler claim Job 后调用需求单 Worker。Worker 经 Runtime 调模型，保存输出检查点，记录候选 Fact 和版本化 Artifact，再做确定性校验及证据复核。用户确认必要事实，审批绑定具体 Artifact 版本，业务 Gate 才允许完成。

**深挖：** 这是一条逻辑链，不是一笔跨所有存储的事务。Artifact 可能已写而事件未提交，多个候选 Fact 也可能部分提交。恢复要用原 commandId／版本继续未完成步骤，不能重新生成同一不可变版本。普通对话并不每次都经过这一整条需求单 Workflow。

## A06．为什么强调 Artifact-first？聊天记录不能作为结果吗？

**回答：** 聊天记录适合保存交互，但难以明确“当前批准的是哪份需求单、依赖哪版事实”。Artifact 用类型、ID、不可变版本、内容引用和来源依赖表示交付物；Evaluation 和 Approval 绑定该版本。聊天说明过程，业务结果有独立身份。

**深挖：** JSON 文本本身不自动具有 Artifact 语义，还需要 Schema、作用域、来源、版本及事件。模型回复和业务 Artifact 也不必一一对应。界面临时 SSE 文字更不能作为持久交付证据。

## A07．Fact 有哪些状态？何时能变成 verified？

**回答：** Fact 状态为 `suggested / unverified / verified / rejected`。模型提取和知识命中只能形成候选；权威企业来源或人工确认才能支持 verified。记录保留 key、值、单位、来源与版本，模型不能靠输出一个 `verified: true` 越过 Host。

**深挖：** 来源可读、来源有权限、来源适用、业务事实已确认是不同命题。用户在自由文本中说“数量大概一万”也不自动等同显式确认事件。确认来源真实性和确认本单采用该值还需区分。

## A08．Fact 修改后，为什么 Artifact 和审批都要失效？

**回答：** Artifact 记录生成时依赖的 Fact 版本。比如数量 v1 为 10,000，用户改为 v2 的 12,000，旧需求单不再描述当前输入，应标为 stale；原审批批准的是旧 Artifact，不能继续覆盖新结果。

**深挖：** 不是直接覆写旧文档，而是重建候选、重新评价并批准新版本。旧版本和旧审批仍保留用于审计。新增一个相关字段也可能改变需求单的完整性，不能只监测已有字段值变化。对应回归包含新增 Fact 使 fresh Artifact 失效。

## A09．为什么 Fact 状态正确还要业务 Evaluator？

**回答：** 一个字段 confirmed，不代表整份产物字段齐全、单位一致、来源可用或下一步动作合理。Evaluator 检查 Schema、必填项、确认状态及依赖一致性。`passed` 与 `approvalEligible` 也应区分：内部一致的缺项草稿可以有明确状态，但仍不具备审批条件。

**深挖：** Schema 解决形状，确定性规则解决可编码约束，模型复核辅助发现遗漏和矛盾，人工审批承担明确决策。任何一层都不能替其他层背书，尤其模型无法保证印刷生产精度。

## A10．事件存储有什么价值？是否所有状态都由事件重放？

**回答：** `ProposalRunEngine` 用事件 reducer 重建业务状态，让事实变更、Artifact 创建、评价、审批和阶段转换可追溯，也能验证非法转换。并非整个应用都只有一条事件流：个人记忆、Plan、Session 和工具账本有各自存储及事务边界。

**深挖：** 事件用于重建本地业务状态，不应在重放时再次调用外部工具。事件 schema 演进、快照、长期日志容量仍需治理。当前存在文件型存储，不能把逻辑 Event Store 说成已经部署了分布式事件平台。

## A11．commandId 与 expectedVersion 为什么都需要？

**回答：** commandId 识别“同一次业务命令”的重试，expectedVersion 检查“基于哪版状态做修改”。同一命令的网络重投先去重，避免因为第一次已推进版本而错误拒绝；不同命令拿着旧版本应冲突，重新读取再决策。

**深挖：** 幂等不等于并发控制。仅 commandId 防不了两个不同操作互相覆盖；仅版本号会使成功命令的重试产生伪冲突。不同组件的 ID 语义不能混用：Tool 的 key 还要绑定输入摘要和作用域。

## A12．为什么需要 Transactional Outbox？

**回答：** 业务事件成功但入队失败会丢任务；先入队再存业务状态可能执行不存在的意图。现有 Event Store 在同次持久化中保存事件与待投递意图，Outbox 再按确定性 Job ID 入队，入队后 ACK。ACK 丢失时重投可以去重。

**深挖：** 它解决业务事件与“投递意图”的一致性，不把文件写入、模型计费、队列和 Artifact 合成全局事务。当前 Outbox 退避最高 30 秒但没有总尝试上限，所以不能说全系统重试都严格有界。见 E17。

## A13．为什么采用本地模块化单体？如何看扩展性？

**回答：** 当前目标是先完成一个本地业务闭环。React 工作台、Node Host、SQLite／文件存储和受控原生解析组成模块化单体，减少部署与跨服务一致性成本。Port 让 Provider、存储等边界可替换。

**深挖：** SQLite 同步调用、整文件写入、全局调度和入口复杂度都有规模上限。扩展前应测真实任务并发、事件大小、索引延迟和失败隔离，再决定迁移哪一层。没有多 Host 压测和并发协议证据，不能只凭接口宣称水平扩展已解决。

## A14．Session、Run、Stage、Job、Turn 有什么区别？

**回答：** Run／Stage 表示业务进度；Job 是可租约调度的工作单元；Session 保存模型执行历史与检查点；Turn 是一次输入对应的模型工具工作；Runtime executionId 标识一次具体执行片。暂停后可以换执行片继续同一 Session／原请求。

**深挖：** 重试次数、业务版本、Session revision 和 Tool 调用 ID 都不能互相替代。一个业务 Run 可能经历多个 Runtime 调用；一个 Plan 又有多个独立子任务 Session。面试白板应写清每个 ID 的产生方、持久化位置与去重范围。

## A15．项目怎样处理租户和权限？达到生产多租户了吗？

**回答：** 数据与调用携带 tenantId／workspaceId／runId，个人记忆另有 actorId；存储、上下文和工具读取在相应作用域校验。本地 Host 决定当前身份，不允许模型从文字中指定 actor 或提升权限。

**深挖：** 作用域隔离测试通过，不等于云端身份认证、企业 RBAC、资源配额和运维隔离已完成。当前是本地 owner 模型，部分 Worker 有 Host 明确委托。Prompt Injection 可能影响文本判断，但不应改变服务端批准记录。

## A16．项目最重要的设计取舍和最大技术债是什么？

**回答：** 最重要的取舍是把模型擅长的理解／探索，和程序必须保证的事实／权限／版本／恢复分开。代价是状态较多、确认步骤和工程成本增加，但故障时能判断哪些结果可信。

**深挖：** 当前值得优先改善的是跨存储部分成功的恢复、非文件工具 unknown 对账、索引总时限、关停 drain、文件锁与持久化一致性，以及真实用户／真实模型评测。它们比继续增加 Agent 数量更贴近实际风险。问题详见 [故障审计 G1–G7](../failure-handling-audit.md)。
