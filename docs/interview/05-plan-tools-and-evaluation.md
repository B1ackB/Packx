# 05｜Plan、工具边界、RAG 与评测

[返回总入口](README.md)。依据：[Plan](../plan-mode.md)、[计划限额与解析](../../src/enterprise/agentPlan.ts)、[计划工作流](../../server/enterprise/agentPlanWorkflow.ts)、[Loop Guard](../../server/runtime/loopGuard.ts)、[证据复核](../requirement-evidence-review.md)、[知识入口](../knowledge/README.md)。

## P01．普通聊天采用 ReAct 还是 Plan-and-Execute？

**回答：** 普通聊天通过模型选择工具、观察结果、继续或回复，属于 Tool Calling／ReAct 风格循环。Plan 模式先生成版本化方案，人工确认后由 Host 顺序执行独立子任务，是有界 Plan-and-Execute。两条路径复用同一个 Runtime。

**深挖：** 不能把模型私有推理链当成可见 ReAct 轨迹；项目可观察的是模型调用、工具调用、结果和状态事件。Plan 的业务确认、预算和调度由 Host 决定，规划文本本身没有执行权限。

## P02．你实现的是多 Agent 并行系统吗？

**回答：** 当前每个计划最多四个独立子任务，各有自己的 Session／上下文，按顺序运行，不支持任意 DAG 和并行写入，也没有递归生成子 Agent。子任务需要消费前一步结果时，应在当前支持的单个子任务内部完成相关工作，而非假设存在依赖调度图。

**深挖：** Session 隔离防上下文串扰，不等于独立文件系统或容器。文件权限仍沿用父任务的受控范围。当前固定对照基线一次调用，Plan 三次调用，证明了确认和两个独立上下文，未证明速度或质量提升。

## P03．如何识别重复动作和工具死循环？

**回答：** Guard 对工具名和输入做规范化 hash，对象键排序、忽略新的 toolCallId；检测周期 1–4 的动作序列出现三轮重复，在第三轮最后一次调用前停止。工具连续失败三次也停止，成功调用清零连续失败。

**深挖：** AAA 在第三次 A 执行前截断，所以只执行两次；ABABAB 在第六个动作前截断，所以只执行五次。连续失败是在结果后累计，第三个失败工具已经执行。对应不可重试码为 repeated_actions／consecutive_tool_failures，不能混说成工具都执行三次才停。

## P04．Guard 如何跨执行片保持？会误杀合理轮询吗？

**回答：** Guard 状态随 Runtime Trace 保存，恢复同 stage／idempotencyKey／session 时取最新序列，保留动作和失败计数。它是 Host 状态，不从模型摘要恢复。合法但相同参数的轮询可能触发停止，这是明确取舍。

**深挖：** 周期超出窗口、每次改无关参数都可能避开模式检测，所以还需要 Runtime、Tool 和 Plan 硬预算。强杀当前执行片可能丢失未落盘 Guard，不能声称无任何窗口。轮询应建模为受控等待／外部任务，而非让模型无限重复读。

## P05．Plan 预算有哪些层？

| 层级 | 当前上限 |
| --- | --- |
| 子任务数 | 每版最多 4 个 |
| 单 Runtime 执行片 | 4 次 Loop 迭代、8 次工具调用、12,000 输入 Token、60 秒 |
| 一个计划版本 | 最多 16 个 Runtime 执行片 |
| 同一任务跨版本 | 最多 4 个版本、累计 32 个 Runtime 执行片 |
| 连续 Plan 失败 | 3 次；仅通过子任务检查点清零 |

**回答：** 规划、失败尝试和恢复都计入额度，重规划、切模式、改目标不能重置任务总量。限制是执行机会，不能换算成精确金额保证；Token、工具成本和真实调用都还需观测。

**深挖：** 一次 Runtime 执行片可能包含多次模型迭代，以及摘要／计数，因此 `totalCalls=32` 不能讲成“全任务最多 32 次所有模型请求”。这也是区分 Runtime call 与 Provider call 的例子。

## P06．子任务说“需要重规划”，Host 怎样处理？

**回答：** 新结果需有 summary、evidence、limitations 和 assessment。Host 校验结构、证据非空及 decision；replan 或空完成证据产生持久 `plan_replan_required`，阻止后续子任务，旧结果、原因、Session 和使用量保留。

**深挖：** 新版引用前版失败和结果节选，用户重新确认后执行；不继承旧审批，不自动反复规划。缺失 assessment 不能自动补通过。证据非空只是一道最低门槛，不证明引用支持结论；执行者漏报问题时仍可能失败。

## P07．计划确认与工具审批、交付审批能合并吗？

**回答：** 当前不合并。计划确认批准的是具体版本的目标、步骤和工具范围；文件审批批准具体路径、输入和预期版本；交付审批批准某个 ArtifactVersion。三者对象和风险不同。

**深挖：** 确认后来源／会话／记忆变化，旧计划不能直接执行。重新规划也不能清除旧 unknown 副作用。若产品未来设计批量授权，需要明确对象与预算，不能把“我同意计划”泛化成任意未来写入。

## P08．为什么加入独立 Reviewer？它与确定性校验如何配合？

**回答：** Schema 和字段规则能识别形状、缺项和状态问题，但难以覆盖自然语言遗漏、无依据表述和证据矛盾。流程先算确定性规则结果，再把候选与原始要求／证据交给独立复核，由 Host 决定 continue、revise、request_input 或 reconfirm_plan。

**深挖：** Reviewer 只报 issues，引用必须来自本轮输入；无证据问题可明确报告不足。规则不过不能因模型说“没问题”而通过；即使规则过，Reviewer 也可能漏检。当前固定脚本对照证明“报告的问题会被挡住”，不证明真实模型发现问题的召回率。

## P09．Reviewer 真的是完全没有工具吗？

**回答：** 工作流传入 `allowedTools: []`，不授权业务／写工具；但当前 BlackxAgentRuntime 会统一追加 `context_read` 和 `execution_ledger_read` 两个只读恢复工具。工作流还要求复核结果没有任何 tool.started／tool.completed 事件，否则不接受为有效复核。

**深挖：** 因此准确说法是“业务工具白名单为空、只读策略、任何工具执行结果都会阻止复核通过”，不是“发给模型的请求里必然没有工具定义”。一轮 iteration、24,000 输入 Token、60 秒限制也不能替代最终事件检查。依据：[call 方法](../../server/enterprise/evidenceReviewWorkflow.ts)、[Runtime 工具追加](../../server/runtime/agentRuntime.ts)。

## P10．自动修订为什么只允许一次、三个字段？

**回答：** 只有符合条件的文字遗漏／无依据表述才可修 title、customerGoal、assumptions，并限定在问题定位覆盖的字段或数组项；额外字段、无关修改、Fact 或权限变化拒绝。新 Artifact 版本再做规则校验与独立复核，第二次仍有问题就停止。

**深挖：** 最多两个复核 Turn 加一个修订 Turn，避免无界反思和成本增长。复核调用前保存不可变 intent；有 intent 无结果的中断标 interrupted_review，不自动重复购买未知调用。这个设计优先可解释与可控，牺牲部分自动恢复便利。

## P11．Tool 接入除了写 execute，还要做哪些事？

**回答：** 要定义输入／输出合同、风险、幂等、超时、结果大小和权限，接入注册与相应路径的 allowlist。普通会话、Plan readTools／executionTools、需求单 Worker 是不同入口，注册成功不等于这些路径都可调用。

**深挖：** 新读取工具若将结果持久进上下文，还要提供来源恢复校验；大结果要可回读；写工具需审批／账本／审计。项目曾有产品检索工具注册后在 Worker allowlist 漏接的历史问题，所以验证要通过真实 Host → Tool → ContextEngine 路径，不能只测函数返回值。

## P12．本地文件和文档解析的安全边界是什么？

**回答：** Host 进行路径、权限、hash／预期版本和逐次文件写入审批；原生解析使用固定可执行程序，在 macOS Seatbelt／supervisor 约束下运行。沙箱不可用时拒绝，不自动降级成无边界 shell。

**深挖：** 这不是整个 Node Host 都在容器中，也不是跨平台沙箱都已验证。解析 PDF 已有文字、DOCX 段落／表格、XLSX 单元格／缓存公式值；没有 OCR、完整 Office 排版还原或公式重算。当前源文件上限 10 MiB，文本预算 1,000,000 Swift 字符，PDF 页／XLSX 表各最多 1,000，仍需看截断标记并分页读取。

## P13．RAG 的实际流程和算法是什么？

**回答：** 资料先经过许可／来源登记、不可变 raw 快照、解析与复核，再进入有版本的块和可重建索引。查询做作用域、地区／日期／型号等过滤，关键词采用字段 IDF，向量采用 SQLite 数据上的精确余弦，混合用 RRF，可选本地 Cross-Encoder 重排，结果通过只读工具进入上下文。

**深挖：** 不应把字段 IDF 直接叫完整 BM25，也不能把 SQLite 精确扫描叫 ANN 向量数据库。默认 lexical-hash 是确定性词项特征，不是神经语义 embedding；本地 E5／reranker 是否启用由当前配置决定。本次没有读取真实业务库来确认运行中实例配置与文档数量。

## P14．为什么切块要保留表头、单位、条件和原文位置？

**回答：** 包装参数脱离试验条件很容易误比。表格单个数值需要表头、单位、方法、温湿度、脚注及型号；因此块和续读返回要保留结构，不能只把数字附近几个字符交给模型。

**深挖：** 块越小定位越准但容易丢条件，越大上下文噪声／成本越高。项目做过切块、句子完整性、overlap 对照，实验并未自动替换已选业务原文版本。chunking 优化不能偷偷重写权威参数或旧选择记录。

## P15．检索高分为什么不能直接成为已确认 Fact？

**回答：** 相似度只说明相关，不证明对应具体型号、地区、日期、方法和适用条件，更不证明允许再分发。资料抽取 human_reviewed 也不等于本单 Fact verified。当前保留 evidenceId／版本／位置，并由 Host 和用户确认是否适用。

**深挖：** 厚度精确数值可以按支持的单位确定性归一化；范围、不等号、未知复合单位不能随意转换。OTR／WVTR 条件不同就不能只比数字大小。没有找到数据应暴露缺口，而不是从产品名称补规格或从论文样品推断在售产品性能。

## P16．重排实验有什么结果？怎么防止挑好看的数字？

**回答：** 2026-09-18 历史冻结实验有 80 题、其中 72 题可回答。同 raw Top 20 候选池重排，完整证据覆盖从 56/72 到 60/72；但已有表格多样化 hybrid 是 59/72，相对现有路径只净增一题。还存在退步题和明显延迟增加。

**深挖：** 历史同候选池 Recall@5 从 84.72% 到 87.50%，MRR@5 从 0.7118 到 0.7660；已有 hybrid 的 Recall@5 并不更低。历史完整查询 P50／P95 从约 64.8／76.1 ms 增到 511.6／1002.5 ms。单机单轮、小语料、已观察题及待人审标注限制都必须报告。本次未重跑该实验，见 [原报告](../knowledge/overlap-rerank.md)，不能报成当前线上质量。

## P17．单元测试、合同测试、Eval、产品 Smoke 分别证明什么？

**回答：** 单元测试检验局部规则；合同测试检查 Adapter／Store 在共同接口下的行为；集成测试跨实际组件检验状态与持久化；固定 Eval 比较冻结场景的指标；本地产品 Smoke 走 HTTP 和固定 Provider 验证装配链路。它们都不自动证明真实模型语义质量。

**深挖：** Fake 能确定性制造限流、迟到、坏输出、来源撤回和崩溃窗口，适合机制回归。真实模型 Eval 要另有模型／数据／预算授权和人工核对。浏览器体验、原生沙箱、负载和故障设备恢复又是不同证据，不能合并成一个“已测试”。

## P18．你会怎样设计真实质量评测？

**回答：** 先冻结任务与通过标准：约束遗漏、错误确认、证据支持率、来源位置、冲突处理、需求单完成时间、人工干预次数和总成本。基线与候选尽量同模型、同任务、同预算；按资料家族／版本划分开发与测试，避免近重复泄漏。

**深挖：** 报告分母、无答案问题、误报／漏报、各语言／条件子组、重复运行分布，以及 Token、延迟、失败率和额外调用。Reviewer 评测特别看漏检、误报、误改；memory 特别看过期偏好、临时需求误泛化和恶意指令。此处是评测设计建议，尚无相应真实模型收益结论。

## P19．日志、Trace、Event、Snapshot 和遥测怎样分工？

**回答：** Event 说明业务变化；Trace 关联一次 Runtime 执行及失败；Snapshot 保存当时受控输入／原文；模型遥测记录调用类型、用途、模型、耗时、Token／缓存用量和状态。ID 连接它们，普通指标不塞 Prompt 全文和 Secret。

**深挖：** ModelTelemetry 当前每个 run 保留最近 200 条并标截断，不是长期无损监控平台。未知价格／用量不当零。Snapshot／Session 仍有敏感正文，必须按 scope 控制；“遥测不存正文”不能说成“项目不保存任何业务文本”。模型异常处理细节见 E19–E20。

## P20．如何回答“这个项目是不是只是 API 套壳”？

**回答：** 调模型本身当然使用 Provider，项目工程重点在把非确定性生成接入可验证的业务生命周期：事实与来源版本、明确审批、持久任务、受控工具、上下文失效和未知副作用恢复。可以用一个“文件已写但账本未完成”的故障推演展示这些工作。

**深挖：** 不应通过贬低框架或夸大商业效果回应质疑。拿出真实入口、状态转换、负面测试和当前限制，说明哪些问题靠 Provider 已解决，哪些由应用负责。若面试官问用户价值，明确尚缺真实售前验收与业务指标，不用代码复杂度替代价值证据。
