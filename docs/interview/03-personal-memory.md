# 03｜个人记忆、版本与失效传播

[返回总入口](README.md)。依据：[记忆系统](../memory-system.md)、[ADR-0026](../adr/0026-confirmed-personal-memory-and-context-dependency.md)、[PersonalMemoryStore](../../server/enterprise/personalMemoryStore.ts)、[Service](../../server/enterprise/personalMemoryService.ts)、[测试](../../server/enterprise/personalMemory.test.ts)。

## M01．项目中的 memory 到底指什么？

**回答：** 要拆成不同对象：原始对话保存交互；工作 messages 保存本轮模型上下文；Fact／Artifact 保存业务事实和交付；KnowledgeStore 保存可检索资料；PersonalMemory 保存用户明确确认的跨任务偏好和笔记。当前个人记忆只在同 tenant／workspace／actor 内使用。

**深挖：** “长期记忆”不等同向量数据库，也不等同模型权重发生学习。Packx 没有自动从所有历史提炼客户画像、共享组织经验或持续微调模型。面试先澄清 memory 的主体、用途和权威级别。

## M02．为什么个人记忆不能直接写成 Fact？

**回答：** “通常用中文、答案简洁”是偏好，属于软上下文；“本单 12,000 件、某材料、某厚度”影响业务交付，要有订单作用域、来源和显式确认。个人偏好不能自动成为本次订单的生产参数。

**深挖：** 即使用户长期偏好某材料，也不能替每单确认。当前明确请求、存储 Fact 和 Host 策略优先于个人偏好；偏好不能授予文件写权限、调整审批或覆盖 Skill。业务安全靠 Host 边界，风格遵循仍取决于模型质量。

## M03．为什么不直接让模型调用 memory_write 保存？

**回答：** 模型只有 `memory_propose`，只能创建待确认候选。用户在面板逐条确认全文后才进入其他任务。这样避免把一次订单、临时意见或恶意文档中的文字自动变成长期偏好。

**深挖：** 工具要求源用户 messageId，Service 校验它确为用户原话且含明确记忆请求信号；该识别是有限正则门槛，并非完整意图理解器。因此人工确认仍是关键。记忆候选写入属于 Host 已允许的工具行为，不能误说每次提候选都要另弹文件审批。

## M04．一条个人记忆有哪些状态，修订期间使用什么？

**回答：** 记录状态为 `proposed / active / change_pending / revoked`，版本中保存内容、来源、时间和确认时间。初始候选确认后 active；已有有效版时提出修订进入 change_pending，旧 activeVersion 继续使用，新 pendingVersion 暂不召回。

**深挖：** 确认修订切到新版本，拒绝修订保留旧版本；初始候选被拒绝则没有有效版本。forget 清空 versions 并撤回记录。不是“有新版本就立即覆盖”，也不把撤回解释为可随时 undo 的软删除。

## M05．如何保证只有本人记忆进入任务？

**回答：** SQLite 主体键包含 tenant、workspace、actor，Host 用认证后的身份构建 scope；API 不接受模型或客户端正文随意注入 actor。召回查询必须匹配三者。

**深挖：** 当前是本地 Host 唯一 owner，并有需求单 Worker 的明确委托条件。测试覆盖跨 actor／tenant／workspace 不可见，但这不是云端 RBAC 完成的证据。跨工作区记忆默认不会自动共享。

## M06．记忆如何召回？为什么没有 embedding？

**回答：** 当前最多 16 条已确认记忆，每条最多 600 字符，足以确定性加载全部有效项。Recall 检查 activeVersion、confirmedAt、撤回状态、到期和来源可用性，再生成有效视图和 binding。没有新增个人记忆 embedding 或提炼模型调用。

**深挖：** 小规模全量读取让确认／撤回语义明确，也避免向量召回漏掉必要偏好。将来记录规模增加时才考虑相关性选择，并保留版本／权限过滤。不能把“没有额外记忆生成调用”说成注入记忆没有主请求 Token 成本。

## M07．有哪些容量限制？过期条目会自动释放确认名额吗？

**回答：** 当前限制为最多 16 条确认项、64 个未撤回项、每条 600 字符、主题 60 字符、每项最多 32 版。达到上限明确报错，需要用户管理条目。

**深挖：** 确认名额检查基于具有 activeVersion 且未撤回的记录；到期或来源失效使其不被召回，但不等于自动撤回并释放所有名额。topic 用 NFKC 和小写规范化检查同主题冲突，不是任意语义冲突检测。

## M08．为什么 revision CAS 与 requestId 都需要？

**回答：** requestId 在主体范围内绑定命令摘要，防重复提交；revision 检查操作基于哪版记忆，防旧页面覆盖新状态。相同 requestId 换 payload 拒绝，不同 requestId 使用旧 revision 也拒绝。

**深挖：** 同一成功确认命令重试应该返回当前记录而不再次确认旧内容。如果期间已经 forget，旧命令重投不能复活旧偏好。这是状态去重的安全性质，不是简单“返回第一次响应字节完全一致”。

## M09．数据库写到一半，记忆状态与审计会分离吗？

**回答：** PersonalMemoryStore 在 `BEGIN IMMEDIATE` 事务里执行命令去重、revision 校验、状态写入和命令事件写入，成功 COMMIT，失败 ROLLBACK。现有故障注入让最后事件 INSERT 失败，重开 SQLite 后确认正文与状态也未提交。

**深挖：** 这只保证个人记忆数据库内部一致。`memory_propose` 的业务事务与通用 Tool 账本是两次提交，可能业务成功而工具 complete 失败。当前它没有文件工具那样的自动对账器，所以不能把数据库事务扩展成端到端 exactly-once。

## M10．删除记忆后，旧摘要会不会再次把它带回来？

**回答：** 这正是 historyBinding 解决的问题。Recall 以当前主体和有效记忆项算 hash；确认新版本、撤回、到期或来源失效会改变有效视图。Runtime 检测 Session 的 historyBinding 不一致，就重建工作历史，丢弃旧派生摘要／助手内容；重新注入当前任务数据和账本回执。

**深挖：** Snapshot 同样绑定 historyBinding，旧快照和嵌套来源不能回读。启用该机制时 transcript 工具只返回用户原话，UI 仍显示完整助手回复；Host 清空 taskContext workingNotes，防另一入口把旧助手笔记再次注入。当前策略是整体失效，未实现最小影响范围的精细依赖切片。

## M11．为什么候选记忆不会让所有任务上下文立即失效？

**回答：** historyBinding 依赖的是有效召回视图，不是整个记忆数据库 revision。未确认候选不进入 recall，提出或拒绝一条未生效修订通常不改变 binding；确认切换版本才改变。

**深挖：** 到期是时间驱动的视图变化，即使没有写入事件，也会在下一次读取中剔除并改变 binding。当前不是主动广播清理所有 Session 的后台服务，而是读取／执行检查点进行核对。已发给 Provider 的请求不能靠撤回“收回”。

## M12．模型调用期间用户改了记忆怎么办？

**回答：** Host 在后续模型请求和检查点等边界重新读取 taskContext binding；变化时停止，不让旧结果继续推动工具副作用或保存为当前完成结果。已有回归在模型等待期间修改记忆，验证后续写工具不执行。

**深挖：** 这是相应执行路径的边界检查，不是撤销所有已经开始的 I/O。暂停 Turn 的旧 binding 也不能原样 resume，需要新请求／重建。成功工具账本必须保留，否则重建上下文反而可能导致重复操作。

## M13．Plan 确认为什么也要检查记忆？

**回答：** Plan 冻结的是完整输入，包括当时有效个人偏好。用户确认计划前如果偏好变化，即使会话 revision 没变，完整 context 比较也能发现，要求重新生成／确认。

**深挖：** 一次小的语言偏好变化可能使计划重新确认，属于当前保守策略的体验代价。未来可研究相关依赖精细化，但不能现在宣称所有偏好变化都能安全热更新。计划确认也不代替每个文件写入的审批。

## M14．来源会话删了、记忆过期了，会发生什么？

**回答：** user_entry 来源要求对应会话仍存在；user_message 来源还检查稳定 messageId、用户角色及原话摘要。来源不可用或 expiresAt 到期就不召回，确认不可用候选也会被拒绝。

**深挖：** 这保证来源引用还可核查，不证明偏好内容永远正确。来源失效与物理删除记忆记录不同；不召回也不意味着删除所有历史副本。到期行为应使用 Fake Clock 测边界，不能靠真实等待让测试不稳定。

## M15．“忘记”是否会彻底删除所有个人数据？

**回答：** 当前 forget 是撤回条目、清空版本正文并停止自动召回。原始用户消息、正式回复、显式业务 Artifact、WAL 和备份不承诺同步物理擦除。没有跨存储全链路清除协调器。

**深挖：** `secure_delete=ON` 也不能证明所有备份和历史副本消失。当前任务中用户原话本身可能包含同样偏好，它仍是这项任务的输入；不能声称 forget 让模型在任何情境都不可能再看到该内容。成功遗忘无自动恢复入口，需要用户重新提供并确认。

## M16．记忆数据库损坏，是否可以忽略它继续回答？

**回答：** 当前选择显式失败，返回 context_failure，避免把“读不到偏好”误当“用户没有偏好”，并让旧派生上下文继续工作。修复存储后再按原身份重试。

**深挖：** 如果未来产品允许用户明确选择不使用记忆，可以设计受控的新输入和 binding；当前不能自动静默降级。可用性与用户约定有取舍，可靠性不是遇到任何错误都勉强输出。

## M17．如何防记忆投毒和 Secret 泄漏？

**回答：** 不从外部文档自动写长期偏好，工具只能引用明确用户请求并提出候选；面板确认、主体隔离、版本与来源验证限制传播。输入对常见 API key、Bearer、私钥等模式拒绝，普通事件只保存 ID、版本、摘要等元数据。

**深挖：** 这不是完整敏感数据分类器，也不能保证模型不会被恶意偏好文字影响。受控状态／模型快照仍可能包含正文，不能说系统完全不持久化文本。权限必须继续由 Host 执行，不能指望一次确认把数据升级为系统指令。

## M18．你如何验证 memory？怎样证明实际有用？

**回答：** 当前测试覆盖确认、修订期间保留旧版、撤回不复活、来源删除、到期、隔离、事务回滚、重启及旧快照拒读。`eval:memory` 使用真实 SQLite、Runtime 和 Session 加 Fake 模型，本次四轮均保留四条固定用户约束，跨任务版本替换和撤回通过，额外提炼／embedding 调用为零。

**深挖：** 这证明正确的偏好进入输入、无效偏好退出输入，不证明模型正确提炼、理解矛盾或遵循偏好。真实评测应比较有／无记忆在同任务的遵循率、误泛化、冲突处理、恶意输入和 Token 增量，并做用户核对；当前标记为 NOT_EVALUATED。
