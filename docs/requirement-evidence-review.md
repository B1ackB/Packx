# 需求单证据复核

需求单候选版本在请求审批前，由 Host 依次运行包装规则校验和独立模型复核。编排位于 `server/enterprise/evidenceReviewWorkflow.ts`，包装语义和可修订字段位于 `server/manufacturing/requirementEvidencePolicy.ts`；复用现有 AgentRuntimePort、ContextEngine、ArtifactContentStore、ProposalRunEngine 和 StageJobScheduler，不修改 Agent Core。

## 当前闭环

1. 原生成 Worker 保留模型输出 checkpoint；对满足严格原文校验的数量提取错误执行确定性纠正，保存纠错检查点，再写入候选 Fact（仍未确认）和不可变 RequirementBrief 版本。
2. 包装规则校验检查 Schema、Fact 权威状态、必填项和 nextAction。结果与用户要求、候选版本、原始 Brief、人工字段、已选证据及附件解析快照一起交给独立 Reviewer。原始计划快照中的模型结果仍是未验证报告。
3. Reviewer 只能输出 `issues`，每项包含 `kind`、JSON 路径 `location`、`evidenceRefs`、`reason` 和 `suggestedAction`。引用必须属于此次输入；只有 `insufficient_evidence` 可以没有引用，并必须说明缺少什么。
4. Host 决定 `continue`、`revise`、`request_input`、`reconfirm_plan` 或 `recover_review`。规则通过且复核完成、问题为空，才继续原有事实确认/审批流程。
5. 当前策略 `packaging-requirement-evidence.v2.6` 按问题选择受限修订。叙述遗漏、无依据表述或草稿与原文相反可修改对应 title、customerGoal、assumptions。`/facts` 的整体遗漏仅授权追加带来源的完整短原文引用，不允许任意改写已有内容或修改 Fact。保留原报告位置，不根据关键词猜测新字段；没有完整原文时不能使用此路径。所有补丁都通过字段/数组项范围检查，额外字段、Fact 修改和无进展被拒绝。
6. 未进入修订范围的问题原样带入第二次复核及最终 Evaluation，不因模型漏报而消失。每次最多修订一次、复核两次；仍有未解决问题则要求人工处理。来源冲突、证据不足及范围变更保留相应业务边界。任何通过都不代替人工 Fact 确认和具体版本审批。
7. 数量纠错仅接受完整原文中的单一、明确整数件数，须单位一致、其他原文无冲突，且当前值不存在或是同源未确认模型候选。不自动纠正估算、范围、每箱、追加、待批准、未知语法、不可读附件或人工录入值。历史错值与原模型输出保留，新值保持未确认。其他字段暂不自动纠正。
8. 系统复核/修订失败、无效输出和无进展使用 `recover_review`；UI 显示复核待恢复及显式新执行入口。Stage 继续使用已有 `needs_input` 暂停状态，不能据此把所有此类任务统计为客户资料不足。


## 持久化、恢复及预算

- 每个候选版本保存 review-input（实际输入快照）、review-call（Runtime 结果）、review（结构化报告）和原有 evaluation；报告绑定 Artifact ID/版本、全部输入 Fact 版本、证据版本和输入摘要。
- `requirement-intake-corrections` 在事实写入前保存纠正决定、完整原文、来源版本、旧事实版本及输入摘要；恢复不重复生成或增加事实版本。最终 Evaluation 含纠正前后值，UI 可展开核对原文。
- 单次自动修订另存 revision-call，新版本通过现有 runtime.execution.linked、artifact.version_created、evaluation.completed 和 stage/approval 事件审计。原版本及报告不覆盖。
- 所有读写使用原租户、工作区、Run 边界。每次异步返回和持久化之前复查租约、取消状态、Fact 版本、知识证据有效性和附件摘要。
- 每次 Runtime Turn 先写不可变调用意图，最多两个复核 Turn 和一个修订 Turn；每 Turn 一个 Agent iteration、24,000 输入 Token、120 秒超时。显式 `allowedTools: []` 禁用所有工具，包括 Runtime 回读助手；数值型工具上限为 1 不开放工具权限。工作流仍拒绝含任何工具执行事件的返回结果。
- `PACKX_REVIEW_MAX_OUTPUT_TOKENS` 可显式指定复核/修订输出预算，必须为正整数且不超过 `PACKX_MODEL_MAX_OUTPUT_TOKENS`。未配置沿用模型上限；不自动提高默认值。实际配置绑定 review-input 和调用意图，计数、上下文预留和生成使用同一值。修改预算后不能复用旧执行身份。
- 收到输出截断时持久化 `output_limit` 并阻断审批，保存原草稿；该错误不允许队列在同一预算下自动重复执行。新预算候选需要显式新执行。失败用量沿现有 ModelTelemetry 记录，未知请求及历史预算不被回填或释放。
- 已保存结果直接复用。若进程在发起模型调用后、结果持久化前崩溃，恢复报告 `interrupted_review` 并进入复核恢复处理，不自动重复购买不确定的调用。租约丢失或取消后的迟到响应不能推进审批。基础设施写入失败保留原队列恢复行为。
- 每个失败报告保留分类；模型失败、超时、预算失败、暂停结果、无快照、无效 JSON/引用、降级 Adapter 或工具调用均不能放行。复核/修订用量和延迟计入需求单指标，成本仍遵守原有未配置价格时显示未知的规则。

## 固定离线对照

运行 `npx vitest run server/enterprise/evidenceReviewWorkflow.test.ts`。

固定候选覆盖要求遗漏、无依据认证、数量矛盾、正确表述以及 Reviewer 漏检。两组均使用同一候选、原始要求和规则：Baseline 只运行确定性校验；候选流程加入固定脚本 Reviewer。该对照展示旧规则会接受结构正确的语义问题，而新流程能阻止脚本报告的问题；同时明确验证 Reviewer 漏报时 Host 无法可靠推断语义遗漏。另有误改 Fact/权限、无效引用、失败/预算、二次复核停止、取消、租户隔离、来源失效、持久化及事件边界恢复测试。

这些是**离线编排与权限边界证据**，不是模型准确率、召回率或业务质量收益。FakeAgentRuntime、M2、知识库和产品 Smoke 的空问题输出是显式 fixture，生产 fallback 仍为无效输出 `{}`，不会按通过处理。之后已进行[真实模型任务对照](evidence/automatic-online-2026-09-26.md)及[复核配置实验](evidence/review-output-2026-09-26.md)。9 月 29 日的预算与输出校验边界见 [ADR-0028](adr/0028-bounded-review-and-current-output-contract.md)，预算对照结果见下文。

## v2.5 历史规则与 v2.6 后续修复

2026-09-29 用户明确要求“改为直接修订，在有必要时再转人工”。因此，草稿的叙述与清楚原文相反时不再仅因 `contradiction` 类型就禁止修订。这是业务规则调整，不是放宽旧实验的评分以取得通过。

v2.5 当时仍需人工处理的情况包括：原始来源相互矛盾、证据不足、客户意图不明、需要修改结构化 Fact/状态/来源、混合报告含不可自动处理的问题，以及一次修订后仍未通过复核。计划范围变化仍需重新确认。模型不能靠把来源冲突标为文字错误来获得事实或审批权限；是否需要人工由独立复核与 Host 字段/版本边界共同约束，语义判断仍可能出错。

离线回归覆盖 PVC 反向叙述自动修订并复核、原版本及 Facts 不变、恢复不重复生成、来源冲突与事实修改请求仍转人工、二次复核失败停止。对历史四份 PVC 报告作权限判断：四处 `/customerGoal` 矛盾均可单独修订；其中一份还要求修改 `/facts`，整份混合报告仍不放行。旧 v2.2 报告、评分、源码归档和费用记录不变；历史评分器不跟随当前生产规则改变。

后续 [ADR-0029](adr/0029-controlled-requirement-corrections.md) 记录 v2.6 的受限修订与数量纠错。原四份 PVC 报告加一份纯遗漏均可使用新修订路径，四份原文明确的数量错误可纠正为未确认候选；这是旧输入/输出的离线回放及脚本补丁验证，尚未使用新提示词重新调用模型，不是线上成功率。

策略版本参与 review-input 摘要，旧 checkpoint 不能静默切换到新策略；需发起新执行。

## 有意保留的限制

2026-09-29 的[输出预算对照](evidence/review-output-budget-2026-09-29.md)完成 60 次生成：提高到 16384 减少了本批截断，但候选控制检查和动作边界未全部通过，未切换默认配置。旧的失败、未知请求与费用预留继续保留。

- 模型修订只改三个文字字段；数量候选纠错由独立的 Domain 确定性规则完成，保持原有事实来源链及未确认状态。未覆盖的语法和字段仍需核对。
- 文本附件提供有长度标记的摘录；PDF/Office 使用已有解析页。图片、未 OCR 扫描件和缺失全文只有元数据可用，不能据此声称已经核对内容，应请求原始证据或人工补充。本次没有新增视觉/OCR 工具。
- 来源引用存在和版本绑定不证明语义蕴含。真实模型仍可能漏检、误报，或在文字里作出错误修订；二次复核和人工审批仍必需。
- 不增加常驻监督 Agent、多轮反思、长期反思记忆、自动重新规划或新依赖。

## 2026-09-30 审批与附件快照边界

会话工作台的 Proposal / Requirement Brief 审批请求必须带 `approvalId`、`artifactVersion`、`expectedAggregateVersion`，均来自用户实际核对的页面。缺失返回 `approval_review_version_required`；版本、审批状态或来源变化返回 `approval_review_stale`，不替用户批准最新版。批准和拒绝使用同一绑定规则。重复请求必须匹配原审批事件的目标、决定、操作者及输入版本；只补齐该审批尚未派发的完成任务，不将旧请求应用到新交付物。

新增附件（包括文字需求单首次增加附件）与附件撤回都会使旧交付物和审批失效。工作台读取、审批、Fact 确认、Worker 完成判定及交付读取共同核对附件快照。新增资料不会自动修改已确认 Fact；员工需明确发起新整理，核对候选或变更后重新审批。历史文件和版本继续保留，过期导出明确标记 `stale`。

前端的整理、事实录入／确认、审批、取消及附件操作绑定会话与本次打开序号。切换任务后的迟到成功、错误与冲突刷新不能覆盖新任务；回到同一任务也不会复用上一次打开时的响应。

回归入口：`server/manufacturing/requirementBriefApi.test.ts`、`server/testing/appMutation.audit.test.ts`。验证使用离线 Runtime 和真实处理函数，不代表真实模型语义质量或浏览器视觉验收。


## 2026-09-30 聊天来源与中断后修订

新增 `customer_messages` 记录用户消息编号、正文和附件引用的摘要。它由 Host 绑定，不能通过字段表单或模型确认；新增用户消息会在读取、审批、完成判定和导出时使旧交付及审批失效。Worker 在执行和提交边界检查同一快照；助手回复和 Session 自身保存不会使新格式的来源失效。历史纯文字需求单比较用户正文；历史计划导入缺少消息摘要时按已存会话 revision 保守核对。来源变化不自动替换已确认事实。

取消后可明确发起新整理；完成交付后可录入待确认修改或生成新版本。修订先持久化旧版本失效与审批失效，再写候选事实或派发执行。重放原执行请求不会主动开启新修订。历史交付内容保持不变，新版本仍需完整核对和审批。

中断留下的 Runtime 检查点和未发布草稿占用其版本号。原 command 重试仍复用原检查点；明确的新执行跳过这些占用的版本，不覆盖、删除或冒用旧结果。Artifact 版本严格递增但可以不连续；旧副作用账本不因跳号变为成功。回归覆盖检查点、纠错记录和草稿落盘后的故障，以及消息在执行期间变化。
