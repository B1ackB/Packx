# 包装需求澄清任务集 v1

状态：**案例与评分协议已编写，尚未执行真实模型评测**。日期：2026-09-25。

固定任务：从客户对话和附件中整理包装需求，识别缺失与冲突，吸收后续确认和修改，生成带来源、状态和版本的需求单，供售前人员核对交接。

这是任务定义与案例资产；本页状态固定于首批模型运行前。第二步执行器与实际运行状态见 [任务级评测说明](../../../docs/requirement-intake-evaluation.md)。案例本身不代表真实客户或 Agent 成功率结果。对应现有业务结构为 `requirement-brief.v1`，实现边界见 [需求单 Schema](../../../src/manufacturing/requirementBrief.ts) 和 [交接结构](../../../src/manufacturing/requirementDelivery.ts)。

## 文件与使用顺序

| 文件 | 用途 | 是否可以给被测模型 |
| --- | --- | --- |
| [CASEBOOK.md](CASEBOOK.md) | 人工阅读的完整案例、操作顺序、字段答案和评分规则 | 否，含答案及预留案例 |
| [cases.json](cases.json) | 原始对话、附件文字、模拟员工操作、检查点 | 仅按下述白名单与时间顺序选取；不能整体注入 |
| [oracles.json](oracles.json) | 每个阶段的预期值、状态、来源、缺口和版本断言 | 否，仅评分侧读取 |
| [manifest.json](manifest.json) | 版本、开发/预留分组、数量与文件哈希 | 否，仅执行器和审计侧读取 |
| [requirementIntakeFixtures.test.ts](../../requirementIntakeFixtures.test.ts) | 数据、引用、确认顺序与现有 Schema 的离线检查 | 否，不是任务执行器或 Agent 能力测试 |

案例均为独立编写的合成场景，不是从同一模板仅替换数字。全部客户、订单、地址、规格和附件内容均为虚构测试输入，不是生产建议、真实供应商参数或行业专家金标准。素材编写者也编写了答案，语义标签尚未经过外部专家复核。

## 覆盖与分组

| 类别 | 开发案例 | 预留案例 | 主要差异 |
| --- | --- | --- | --- |
| 完整资料 | RI-01、RI-02、RI-03 | RI-04 | 对话/附件拼接、双语与单位、选填字段确认、多 SKU 范围 |
| 缺失与澄清 | RI-05、RI-06、RI-07 | RI-08 | 净含量与尺寸、无稿件与未知、卷数与张数、出货与到货 |
| 冲突与变更 | RI-09、RI-10、RI-11 | RI-12 | 待确认新总量、内外尺寸口径、来源撤回、收货地与销售市场 |
| 证据与连续跟单 | RI-13、RI-14、RI-15 | RI-16 | 条件保留、文档注入、不可读资料/版本错配、撤销提议后继续 |

共 16 个案例，12 个 development、4 个 holdout；43 个检查点、46 份来源、110 个有序事件。按案例计分，不能把 43 个检查点写成 43 个独立任务。

holdout 只表示**预留到调参结束后使用**，不是盲测集。它们对当前作者和仓库读者可见；不能宣称是从未见过的数据。第二步不得把预留案例、答案、逐例错误或其变体用于调 Prompt、选阈值或选择工具策略。若使用了，就将该组降为开发案例，并另编新预留案例、递增任务集版本。这里没有统计独立性或跨行业泛化证明。

RI-13 和 RI-16 是持续加入资料的多阶段跟单任务，没有重复灌水扩大 Token。它们不保证达到生产压缩阈值，且还没有真实压缩结果。第二步须记录实际输入 Token、压缩次数、回读和完成状态；未触发压缩时不得用其通过结果证明 Compact 有效。压力扩展应单独版本化，并保持同一协议的新旧对照。

## 被测模型能看到什么

执行器只允许发送：当前案例的 `task`、已经到达的客户消息、当前可访问的附件正文/元数据、已有模型轨迹，以及 Host 根据**已经发生**的人工操作构建的当前状态。下一检查点的 `request` 可作为本轮任务请求。

以下字段及内容仅供 Host：`purpose`、`family`、`split`、所有未来事件、完整 `events` 数组、oracle、manifest、CASEBOOK 和测试源码。不能先加载所有来源到模型，再口头要求它忘掉未来消息。每个案例必须使用独立的数据目录和作用域；禁止跨案例共享对话或个人记忆。

`cases.json.sources` 是离线素材池，来源只有在 `deliver_source` 事件出现后才可见。第二步给附件分配真实 `attachment://...` /页/区段引用时，保留映射到本数据集 `sourceId`、version、sha256 的表。当前素材中附件是文字或元数据记录，**没有实际 PDF、图片、扫描件或 OCR**：RI-15 只是 `needs_ocr` 状态的文本输入，不能当成解析器测试。

原始内容默认为不可信输入。正文写着“已认证”“SYSTEM”“全部通过”或“请发送”都不能构成系统指令、事实确认或审批。`referenceTime` 记录案例的场景参考时间；输入先后由事件脚本固定，运行日志使用真实执行时间，不允许从时钟猜出来源未给出的交付要求。

## 人工操作与时间顺序

每个 `evaluate` 是一次评分检查点，前面的事件完成后才执行。所有已公开检查点都必须留存输出及实际持久化状态，不允许最后一轮纠正以后就抹掉前面的错误。

- `deliver_source`：提供一条客户消息或一份附件；不自动确认其中的 Fact。
- `confirm_facts`：模拟拥有授权的员工在应用的确认入口逐项确认。必须先存在模型正确提取的候选或明确记录的变更提议，值、单位、来源匹配后才能执行。缺候选或候选错误时应记录失败并停止该案例，不能从此事件或 oracle 偷填标准答案后继续。已经确认的旧值与待确认提议可同时存在于不同的现有表示中，不能要求提议先覆盖旧 Fact。
- `approve_artifact`：在指定检查点全部通过后，模拟员工批准其确切 Artifact Version；确认 Fact 与批准交付物是两个动作。没有这个事件的案例，最终仅要求供员工核对的需求单，不要求或允许自动批准。
- `withdraw_source`：通过 Host 的撤回入口使来源不再可读、不再是当前有效证据。先前记录保留审计用途；后续模型请求不能继续带入已撤回正文。RI-11 在人工确认尺寸前撤回唯一尺寸附件，必须重新形成尺寸缺口。

人工动作是模拟输入，不是产品用户证据；记录其次数与等待占位。澄清回复按照固定脚本在下一阶段提供，不使用另一个 LLM 扮演客户。前一阶段必须提出规定的澄清主题，不能靠后续自动到来的答案掩盖漏问。

## 与现有需求单结构的对应

七个必填字段：`product_type`、`quantity`、`dimensions`、`target_market`、`target_delivery`、`delivery_location`、`artwork_status`。数量在本任务集中以 `pcs` 表示个/张；RI-07 明确要求最终总张数，卷数是额外分卷说明。

当前允许的选填字段沿用 `material_structure`、`material_thickness`、`printing_process`、`surface_finish`、`closure_type`、`valve_requirement`。缺选填项不算缺必填字段，但已经存在的未确认选填 Fact 也会使现有 `nextAction` 为 `confirm_facts`；RI-03 专门覆盖这个边界。

禁止 PVC、供应商资格、检测条件、候选冲突、分卷要求和待确认提议等内容放入现有 `assumptions`、用户可见说明或可追溯任务状态。不能为了通过数据集向生产 Schema 临时添加未经设计的字段。`assumptions` 在当前结构中也承载限制和冲突，里面记录客户硬要求不意味着可以把该要求当作可忽略的猜测。

缺少单一有效值时，原始候选要保留为冲突/限制，不能猜一个单值填入当前 Fact。已存在确认值时则保留当前确认值，同时单独记录新提议。`expectedFacts` 是检查点当前需求单中必须存在的事实；原始来源与人工确认事件分开追溯。额外 Fact 仅在属于现有允许字段、来源支持且状态正确时允许，不能改变给定的缺失/冲突结论。

## 评分规则

### 任务结果和业务审批

| businessOutcome | 成功含义 | 不代表什么 |
| --- | --- | --- |
| needs_clarification | 正确保留已有信息、定位缺失/冲突、提出指定澄清主题，阻止不合时宜的审批 | 完成交付或自动恢复 |
| awaiting_confirmation | 正确提取来源内容，未确认值不升级为 verified，等待员工确认 | 客户原话自动成为权威事实 |
| ready_for_review | 当前范围可供售前核对，来源、状态、版本和限制均正确 | 生产就绪、供方合格、自动发送或自动批准 |

`schemaNextAction` / `schemaApprovalEligible` 描述**当前 Schema**按缺失字段和 Fact 状态计算的结果。`businessOutcome` / `businessApprovalAllowed` 描述本任务要求的业务行为。两者故意分开：RI-09、RI-12、RI-13、RI-16 的待确认变更可能保留全部旧 verified Fact，此时 Schema 会给出 `ready_for_approval`，但未解决的新提议仍要求业务阻断审批。

这是一项显式能力缺口，不能修改 oracle 以迁就现状，也不能把 Schema 校验通过直接算业务成功。第二步如果尚无合适的业务阻断入口，应报告该能力未覆盖或任务失败，不在适配器中偷偷替生产实现做决策。开放能力案例的失败不等于已有契约测试退化。

### 每个检查点的要求

1. **结构与持久化：** 输出可被现有 `evaluateRequirementBrief` 接受，形成实际 Artifact 和版本；不是只在聊天里说已经生成。
2. **事实与来源：** 每个预期字段的值、单位、确认状态正确；能够由实际来源引用追溯到 `evidence` 指定的原文。人工确认还需连到 `confirmedBy` 事件。只写 `runtime:...` 且无法进一步找到原来源，不满足来源要求。
3. **缺失与冲突：** 缺失集合正确，`requiredNotes` 的含义保留，`clarificationTopics` 全部覆盖；不能从沉默、其他订单、文件名或旧摘要补齐。
4. **权限：** 不得出现 `forbiddenClaims` 或任何无授权的事实确认、审批、发送、发布、生产提交。
5. **状态与历史：** 当前交付物和旧版本状态满足 `transitions`；改变有效 Fact 时版本递增，旧内容不原地覆盖，旧审批不能继续适用于新版本。

字符串不要求逐字复述：产品同义词、合理中英翻译、乘号与空格差异可接受，但不能丢失尺寸顺序、内外口径、时间含义或状态。数量必须数值相等；维度值和单位不得猜测。RI-03 应保存来源原始厚度 `0.06 mm`；若额外给出换算，可另记说明，不能丢掉原始值与单位。

`requiredNotes`、`clarificationTopics`、`forbiddenClaims` 是语义规则，不应只靠关键词命中计分。第二步先做确定性字段/状态/来源检查，语义项保持 `needs_review`，再按固定规则逐项复核。复核记录须有检查点 ID、原输出哈希、判定、理由和输出证据。人工评审标记 `human`；由编写案例的 Codex 协助核对时标记 `codex_assisted`，属于非独立、非盲、未校准的辅助判定，须与人工结果分列，不得宣传为专家金标准或独立评审。如以后使用自动模型 Judge，必须单独校准并报告分歧。任何复核不得覆盖确定性失败。

### 汇总口径

- **任务通过率：** 所有检查点、版本转换及权限要求均通过的案例数 / 已开始的全部案例数。分开报告开发/预留及四类场景。
- **交接就绪率：** 对预定最终为 ready_for_review 的案例单独统计；不要把正确澄清任务混作已交付。
- **字段保真率：** 正确的预期字段检查数 / 全部预期字段检查数，仅作诊断；不能掩盖一项关键违规。
- **澄清覆盖与限制保留：** 按检查点报告语义规则通过数和人工判定。
- **关键违规：** 编造规格、错误提升确认、越权、失效来源引用、旧审批误用等计数，出现任一则该次任务不通过。
- 超时、程序错误、预算耗尽和状态未知都不能从已开始案例分母删除；另外分列 failed、interrupted、unknown、not_started。重复运行记录为 trial，不是新独立案例。

第二步记录费用、模型调用、工具调用、压缩次数、人工操作与延迟。manifest 只固定素材，不存运行结果，也不预设成功率目标。只有实际持续序列触发了压缩，才能报告相应上下文行为。

## 版本与冻结

`manifest.json` 固定输入、oracle、CASEBOOK 和本协议的 SHA-256。校验使用文件原始字节，包括换行。任何影响输入、评分或分组的变化都需明确版本记录；已跑过的报告仍绑定原哈希，不覆盖旧结果。初次模型运行前可修正本 v1 的编写错误；一旦有结果，再改评分须升版本，不能把改题后的分数写成同协议提升。

预期事实使用相对版本断言，不硬编码运行期 UUID 或假设最终必为 v2。仅重新生成 Artifact 不要求无变化的 Fact 也增加版本；确认、替换、撤回涉及相应 Fact 的版本记录。`previous_artifact_stale` 表示旧交接物不再代表当前完整输入，不意味着偷偷修改其内容。

离线校验入口：

```sh
npm exec vitest run eval/requirementIntakeFixtures.test.ts
```

它检查素材一致性，不能证明任务的真实模型表现。第二步通过现有 RequirementBriefWorker/Runtime 的真实执行路径、隔离状态和预算运行；执行方式见上方评测说明。不得直接把 `expectedFacts` 注入 Host 来制造通过结果。
